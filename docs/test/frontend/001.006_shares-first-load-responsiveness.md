# Test Case: 001.006_shares-first-load-responsiveness

## Test Objective

Verify the Shares tab paints share rows promptly on first open (`shareHook` refactor + `ListShares` settings-cache optimization): `GET /api/shares` p50 under 1s on the test host, and the tree shows rows on the first data paint with no multi-second empty state.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Backend prerequisite: optimized build deployed — five consecutive `curl -s -o /dev/null -w '%{time_total}\n' http://192.168.0.68:3000/api/shares` all return 200. If the first call is slow but later calls are fast, note cold-start vs steady-state separately; do not conflate the two
3. Record share count baseline: `curl -s http://192.168.0.68:3000/api/shares | jq length` → N (expected N > 0)
4. Frontend at `http://localhost:3080/` with `API_URL=http://192.168.0.68:3000/`; WS indicator green; no console errors after load

**If any preparation step fails** (addon not started, UI unreachable, zero shares), **skip** and document.

## Execution

1. **API timing:** run `for i in 1 2 3 4 5; do curl -s -o /dev/null -w '%{time_total}\n' http://192.168.0.68:3000/api/shares; done` → record all five; steady-state (calls 2–5) must all be under 1s
2. **Cache check:** `PUT /api/settings` with `standard_share_names:new` → 200; `GET /api/shares` must show `is_hidden:true` on `addons`/`addon_configs` on the very first call after save (proves the SettingEvent refreshed the mode cache with no restart); restore `both` → first call shows nothing hidden
3. **First paint:** hard-reload the app, open the Shares tab, start a timer on navigation → stop when the first share row is visible → record paint time; the tree must show rows (or a loading skeleton) immediately — never a populated chrome with an empty tree for multiple seconds
4. **No empty flash:** with Playwright network inspection, confirm `GET /api/shares` fires once on tab open and the tree renders from that response without waiting for a later WS `shares` event

**Assertions:**

- Steady-state `GET /api/shares` under 1s on all measured calls
- Mode switch visible on first `GET /api/shares` after settings save, no restart
- First share row visible within 2s of opening the tab on the test host
- No console errors, WS stays green throughout

## Validation

1. Cleanup: `PUT /api/settings` with `standard_share_names:both` → 200 (if changed); verify tree back to baseline
2. Check logs: addon logs no `ERROR`/`panic` from shares listing
3. Record API timings + paint time + screenshot of populated tree as evidence

**Success criteria:** API fast in steady state, cache refreshes on settings save, first paint shows rows promptly with no empty flash, settings restored, no log errors.
