# Test Case: 007.005_settings-readonly

## Test Objective

Verify Settings read-only mode (`read_only:true` via `evdata.hello.read_only` or addon `ro` flag) disables all controls: `TextFieldElement`, `SwitchElement`, `MuiChipsInput`, `SelectElement` disabled, `Apply`/`Reset` remain disabled even when attempting to dirty, and form `disabled: readOnly` propagates.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Determine readOnly flag: `curl -s http://192.168.0.68:3000/api/settings` not needed; `GET /api/hello` or WS `hello.read_only` via `useGetServerEventsQuery` → note `read_only` bool. If `false` by default, simulate by mocking `evdata.hello.read_only=true` via `msw` override (`getMswServer().use(http.get(.../api/hello) → {read_only:true})`) or by setting addon option `ro:true` and restarting (if available). Document method used.
3. Frontend at `http://localhost:3080/` → Settings tab loads; if simulating, apply mock before navigating to Settings
4. Verify baseline `General` panel loads without error

**If preparation fails** (cannot simulate readOnly), **skip** and document reason.

## Execution

1. Enable readOnly simulation (mock or addon restart with `ro:true`) → reload `http://localhost:3080/` → click Settings
2. Verify `General` fields: `input[name="hostname"]` `toBeDisabled()`, `input[name="workgroup"]` `toBeDisabled()`, `Local Master` switch `toBeDisabled()` (check `SwitchElement` input `disabled` attr or `aria-disabled`)
3. Check `Devices` panel: `Bind All Interfaces` checkbox disabled, `Multi Channel` switch disabled
4. Check `Access Control`: `MuiChipsInput` input disabled, `add suggested default allow hosts` button disabled (`aria-label` button `disabled`)
5. Check `Telemetry`/`HomeAssistant`: selects/switches disabled
6. Verify bottom bar: `Reset` and `Apply` (`form="settingsform"`) both `toBeDisabled()` regardless of attempted edits (try native setter on `hostname` → buttons should stay disabled because `disabled: readOnly` form-level)
7. Attempt to trigger dirty via native setter (`-bad-`) → verify `formState.isDirty` remains false or buttons stay disabled (form disabled prevents dirty)
8. Verify network: no `PUT /api/settings` should fire when clicking disabled Apply (not clickable)

**Assertions:**

- All controls disabled when `read_only:true`, bottom bar disabled, no dirty, no PUT

## Validation

1. Disable readOnly simulation (restore mock or `ro:false` + restart) → reload → verify controls re-enabled (`not.toBeDisabled()`), dirty works again (edit workgroup → Apply enabled)
2. Check logs: `ha apps logs` no `ERROR` after toggle, `ha core logs` no `custom_components.srat` traceback
3. Check console: no `act` warnings from disabled form
4. Document simulation method and evidence: screenshots with disabled styling (greyed, `Mui-disabled` class)
5. Cleanup: ensure addon back to `read_only:false` original state

**Success criteria:** Read-only disables all Settings controls and Apply, re-enable restores editability, no log errors.
