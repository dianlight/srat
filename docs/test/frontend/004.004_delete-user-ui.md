# Test Case: 004.004_delete-user-ui

## Test Objective

Verify DELETE USER via UI: `Users` → select user → `UserDetailsPanel` `DeleteIcon` → `material-ui-confirm` dialog (`Delete <username>?` with acknowledgement) → confirm → `DELETE /api/user/{username}` → toast → `selectedUserKey` cleared and tree no longer contains user, `pdbedit -L` confirms removal.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Ensure deletable test user exists: `TEST_USER="u$(date +%s | tail -c 6)"` with `TEST_PASS="Aa$(date +%s | tail -c 5)!"`; if not present `POST /api/user` → 201; record `PRE_COUNT=$(curl -s http://192.168.0.68:3000/api/users | jq length)`
3. Ensure test user is not `admin` (admin cannot be deleted via `DELETE /user/{username}`; deletion is only for regular users; admin updates go via `PUT /useradmin`)
4. Frontend at `http://localhost:3080/` → Users tab → expand `group-users` → verify `TEST_USER` visible in tree; selecting it sets `localStorage["users.selectedUserKey"]=TEST_USER`
5. Snapshot baseline: screenshot of Users before delete, list via `GET /api/users | jq -r '.[].username'`

**If preparation fails** (no deletable user, UI not reachable), skip.

## Execution

1. Navigate `http://localhost:3080/` → Users → click `TEST_USER` → verify `UserDetailsPanel` header shows username and `Delete` button (`DeleteIcon` with `aria-label` delete or `Tooltip` delete)
2. Click `Delete` → confirmation dialog appears: title `Delete $TEST_USER?`, description `Do you really want to delete this user?`, acknowledgement checkbox/text `I understand that deleting the user will remove it permanently.` (from `UserActions`/`useConfirm` config). Verify via `browser_snapshot` or `getByText(/Delete .*?\?/)` and acknowledgement text
3. Check cancellation path first: click `Cancel` (or press Esc) → dialog closes, no network call, user still in tree (`GET /api/users` still contains `$TEST_USER`), `selectedUserKey` unchanged
4. Re-click `Delete` → now confirm: tick acknowledgement if required then click `Confirm`/`Delete` (material-ui-confirm Confirm button) → verify `browser_network_requests` shows `DELETE /api/user/$TEST_USER` → 200
5. Verify toast `User $TEST_USER deleted successfully` appears
6. Verify UI post-delete: `selectedUserKey` cleared (`localStorage.getItem("users.selectedUserKey")` → null or different), right panel shows placeholder `Select a user from the list to view details`, tree `group-users` no longer lists `$TEST_USER` (if last user in group, group may disappear; chip count decrements)
7. Verify backend: `curl -s http://192.168.0.68:3000/api/users | jq -r --arg u "$TEST_USER" '.[] | select(.username==$u) | .username'` → empty; `GET /api/users` length == `PRE_COUNT-1`
8. Verify Samba: `docker exec addon_local_sambanas2 pdbedit -L | grep $TEST_USER` → not found; `smbclient -L //127.0.0.1 -U $TEST_USER%$TEST_PASS` → `NT_STATUS_LOGON_FAILURE` (or `NT_STATUS_NO_SUCH_USER`)
9. Verify failure path: attempt `DELETE /api/user/$TEST_USER` again → 404; UI toast for non-existent delete not triggered unless manually called

**Assertions:**
- Confirm dialog requires explicit confirm, cancel leaves state intact
- Delete 200 removes from API, tree, Samba, and clears selection; second delete 404
- No lingering selection or stale details panel

## Validation

1. Try deleting `admin` via UI: button should either be hidden/disabled for admin or backend rejects; verify no admin deletion occurs (protect admin)
2. Logs: `ha addons logs local_sambanas2 | tail -30` → no ERROR; `ha core logs | tail -20` clean
3. Verify `testparm -s` valid and remaining shares/users consistent
4. Final screenshot of Users tab after delete (group counts updated)

**Success criteria:** Full delete lifecycle via UI succeeds, backend and Samba confirm, selection cleared correctly, no errors.
