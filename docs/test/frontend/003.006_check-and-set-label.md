# Test Case: 003.006_check-and-set-label

## Test Objective

Verify CHECK FILESYSTEM and SET LABEL for an unmounted data partition: check reports a clean filesystem without errors, and after setting a new label the new label appears in the Volumes tree (with the mandatory post-label freshness assertion) and the partition remains mountable without errors.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `state: started`; `curl -s http://192.168.0.68:3000/api/health` → 200 with `alive:true`
2. Target partition (non-destructive — check is read-only, set-label preserves data): `TEST_PARTITION_ID=ata-WD_PC_SN740_SDDPNQD-512G-2006_23482W805056-part1` (`system:false`, ext4)
3. Label params: record current label `TEST_OLD_LABEL=$(curl -s "http://192.168.0.68:3000/api/filesystem/label?partition_id=$TEST_PARTITION_ID" | jq -r .label)`; new label `TEST_NEW_LABEL=SRATLBL01` (must differ from current; satisfies ext4 `labelRule ^[^\x00/]{1,16}$` — verify via `curl -s "http://192.168.0.68:3000/api/filesystem/support?fstype=ext4" | jq .labelRule`)
4. Verify support flags: `curl -s http://192.168.0.68:3000/api/volumes | jq --arg pid "$TEST_PARTITION_ID" '.[] | select(.partitions[$pid]!=null) | .partitions[$pid].filesystem_info.support | {canCheck, canSetLabel}'` → both `true`
5. Frontend at `http://localhost:3080/` via `API_URL=http://192.168.0.68:3000/ SUPERVISOR_URL=http://192.168.0.68/ mise run //frontend:dev:remote` → `bun tsc --noEmit` green, WS `ws://192.168.0.68:3000/ws` reachable
6. Both actions are gated on unmounted state (`PartitionActionItems.ts` — `Check Filesystem` and `Set Label` only when `!isMounted`); ensure partition is unmounted before starting (via UI UNMOUNT or `DELETE /api/volume?mount_path=<path>`). If a share is attached (`share != null`), delete it first.

**If any preparation step fails**, skip and document.

## Execution

1. Navigate `http://localhost:3080/` → click `VOLUMES` tab → expand disk `WD PC SN740` → select `$TEST_PARTITION_ID`. Confirm detail panel shows `Not Mounted` and Actions contain `Check Filesystem` and `Set Label`.
2. Check via API: `curl -s -X POST http://192.168.0.68:3000/api/filesystem/check -H "Content-Type: application/json" -d "{\"partitionId\":\"$TEST_PARTITION_ID\",\"autoFix\":false,\"force\":false,\"verbose\":true}"` → 200 `Check operation started`. Poll `GET /filesystem/state?partition_id=$TEST_PARTITION_ID` up to 120s → `isClean:true, hasErrors:false, isMounted:false`.
3. Check via UI (counter-check): click `Check Filesystem` → dialog `Filesystem Check: <label>` opens → run with `Auto Fix` OFF → progress completes with success message, no failure alert.
4. Set label via UI: click `Set Label` → dialog `Set Filesystem Label: <label>` opens → enter `Label=$TEST_NEW_LABEL` → Apply → success toast. Dialog validates against `labelRule`; invalid input blocks Apply with helper text.
5. **Mandatory freshness assertion** (skill Step 7a — catches #1063-class bugs): within 30s of the set-label success, assert `GET /api/volumes` partition `name` equals `GET /filesystem/label?partition_id=$TEST_PARTITION_ID` (`label` field). If they differ after 30s, do NOT re-apply the label — record as stale-DiskMap bug and restart the addon to clear the cache before continuing.
6. Verify Volumes tree shows new label: re-select partition in UI, tree node/detail header shows `$TEST_NEW_LABEL` (screenshot).
7. Mount the partition: click `Mount Partition` (or `POST /api/volume/mount` with stored `mountPointData`) → detail shows `Mounted`, `Mount Point /mnt/$TEST_PARTITION_ID`.
8. Verify mount via API: `curl -s http://192.168.0.68:3000/api/volumes | jq --arg pid "$TEST_PARTITION_ID" '.[] | select(.partitions[$pid]!=null) | .partitions[$pid].mount_point_data | to_entries[0].value | {is_mounted, path, fstype, disk_label}'` → `is_mounted:true`, `disk_label==$TEST_NEW_LABEL`. Host check `lsblk -o NAME,MOUNTPOINT,FSTYPE,LABEL` (in `app_local_sambanas2` container) shows mountpoint + `LABEL=$TEST_NEW_LABEL`.
9. Write/read smoke (optional): `docker exec app_local_sambanas2 sh -c "echo hello > /mnt/$TEST_PARTITION_ID/.srat_lbl_test && cat /mnt/$TEST_PARTITION_ID/.srat_lbl_test && rm /mnt/$TEST_PARTITION_ID/.srat_lbl_test"` → `hello` with no I/O error.

**Assertions:**

- Check task completes with success; `GET /filesystem/state` reports `isClean:true, hasErrors:false`
- `GET /api/volumes` partition `name` equals `$TEST_NEW_LABEL` within 30s of set-label (freshness assertion)
- `GET /filesystem/label` returns `$TEST_NEW_LABEL`
- Volumes tree/detail displays new label (screenshot evidence)
- Mount succeeds after check + set-label with `is_mounted:true`, no `ERROR` in addon logs
- FS write/read round-trip succeeds without errors

## Validation

1. WS freshness: `volumes` event payload after set-label and after mount matches concurrent REST `/api/volumes` within 2s (see #971 class).
2. Logs: `ha addons logs local_sambanas2` tail → no `ERROR/panic` for check/set-label/mount; `ha core logs` → no `custom_components.srat` tracebacks.
3. Negative check (optional): enter an invalid label (e.g. containing `/` for ext4) in the Set Label dialog → Apply blocked with validation helper (no API call).
4. Leave partition mounted with new label (per test objective — do not revert label). Record final state (`$TEST_OLD_LABEL` → `$TEST_NEW_LABEL`) in evidence.
5. Leave no test shares behind; lab mode / settings unchanged.

**Success criteria:** Check reports clean with no errors; new label visible in Volumes tree within 30s of set-label (no restart needed); partition mounts cleanly with no errors; API, WS, and UI agree on label + mount state.
