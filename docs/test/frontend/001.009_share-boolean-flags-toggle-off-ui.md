# Test Case: 001.009_share-boolean-flags-toggle-off-ui

## Test Objective

Verify that boolean share flags (`guest_ok`, and by extension `timemachine`, `recycle_bin_enabled`) can be turned back OFF via the UI edit form and that the OFF state persists (regression test for issue #1191, where `PUT /api/share/<name>` with `guest_ok:false` returned 200 but kept `guest_ok:true`).

## Preparation

1. Ensure the SRAT addon is running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Ensure frontend is served at `http://localhost:3080/` (via `API_URL=http://192.168.0.68:3000/ SUPERVISOR_URL=http://192.168.0.68/ mise run //frontend:dev:remote`)—page loads with no JS errors
3. Navigate to Shares: `http://localhost:3080/` → click Shares tab (`#full-width-tab-2`) → expand group containing the target share
4. Verify at least one share exists in the list (create one via `001.001` preparation if needed)
5. Record the share name to edit: `EDIT_SHARE=$(curl -s http://192.168.0.68:3000/api/shares | jq -r '.[0].name')`
6. Record the initial flag state: `curl -s http://192.168.0.68:3000/api/shares | jq --arg n "$EDIT_SHARE" '.[] | select(.name==$n) | {guest_ok, timemachine, recycle_bin_enabled}'`

**If any preparation step fails** (no shares exist, UI not accessible, API unreachable), the test must be **skipped**.

## Execution

1. Open the share edit dialog for the recorded share (`SharesTreeView` → `ShareActions` → Edit) and verify the form is populated with current values
2. Enable Guest Access in the `ShareEditForm` toggle and select Apply; wait for the success notification/toast
3. Verify via API that the flag turned ON: `GET /api/shares` shows `guest_ok:true` for the share
4. Re-open the edit dialog, disable Guest Access, and select Apply; wait for the success notification/toast
5. Verify via API that the flag turned OFF: `GET /api/shares` shows `guest_ok:false` for the share (this is the #1191 regression assertion — it stayed `true` before the fix)

**Assertions:**

- Success notification/toast appears after each share update
- Network `PUT /api/share/${EDIT_SHARE}` returns 200 for both the ON and OFF updates
- `PUT` response body for the OFF update echoes `guest_ok:false` (not `true`)
- `GET /api/shares` reflects `guest_ok:true` after step 3 and `guest_ok:false` after step 5
- Other share properties remain unchanged unless explicitly modified

## Validation

1. Verify the final share state via the SRAT API:
   ```bash
   curl -s http://192.168.0.68:3000/api/shares | jq --arg n "$EDIT_SHARE" '.[] | select(.name==$n)'
   ```
2. Confirm `testparm -s` still contains the share block after soft restart: `ssh root@192.168.0.68 "docker exec app_local_sambanas2 testparm -s 2>&1 | grep -i \"\[$EDIT_SHARE\]\""`
3. Check WS `shares` event: `ws://192.168.0.68:3000/ws` stream contains updated `event: shares` within 5 seconds
4. Verify share remains functional: can still be viewed and deleted via UI

**Success criteria:** Guest Access toggled ON then OFF via UI, each state verifiable through API round-trip, `smb.conf` intact, and the share remains functional.
