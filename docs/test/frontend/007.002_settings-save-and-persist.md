# Test Case: 007.002_settings-save-and-persist

## Test Objective

Verify Settings save flow: edit General fields (hostname/workgroup), trigger dirty state, `Apply` commits via `PUT /api/settings` → `GET /api/settings` reflects change, persists after addon restart, `Reset` reverts dirty, and bottom bar dirty gating works. Also verifies `POST /api/settings/homeassistant/...` not needed for this case.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Fetch baseline settings: `ORIG=$(curl -s http://192.168.0.68:3000/api/settings)`; `ORIG_HOST=$(echo $ORIG | jq -r .hostname)`; `ORIG_WG=$(echo $ORIG | jq -r .workgroup)`; save for cleanup
3. Ensure workgroup valid per `WORKGROUP_REGEX` `^[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,13}[a-zA-Z0-9])?$` length 1-15; hostname per `HOSTNAME_REGEX` length 1-63
4. Frontend at `http://localhost:3080/` with `API_URL=http://192.168.0.68:3000/` → Settings tab loads with `General` selected; `bun tsc --noEmit` green, WS green, no console errors
5. Check readOnly: `curl -s http://192.168.0.68:3000/api/hello | jq .read_only` or `evdata.hello.read_only` → false; if true skip (read-only hides Apply)
6. Clear any dirty: reload page, verify `Reset` and `Apply` buttons disabled (`toBeDisabled()`)

**If any preparation step fails** (read_only true, settings unreachable), **skip**.

## Execution

1. Navigate `http://localhost:3080/` → `Settings` → verify `General` heading; `Apply`/`Reset` disabled
2. Edit `Workgroup`: `getByLabelText(/Workgroup/i)` → clear and type `TESTWG` (unique, e.g. `TWG$(date +%s | tail -c 4)`, satisfying regex, ≤15 chars); blur → verify form becomes dirty: `Apply`/`Reset` become enabled (`not.toBeDisabled()`)
3. Test Reset: click `Reset` → fields revert to `ORIG_WG`, buttons disabled again (dirty cleared). Re-edit to `TESTWG` again for save flow
4. Edit `Hostname` to `test-host-$(date +%s | tail -c 4)` (lowercase, satisfies hostname regex, 1-63) or keep orig if hostname change risky; at minimum one field dirty
5. Click `Apply` (`getByRole('button', {name:/^Apply$/i})` with `type=submit form=settingsform`): verify network `PUT /api/settings` fired (200), `browser_console_messages` no error, toast or silent reset occurs (`reset(res)` called)
6. After Apply, buttons disabled again (form reset with new values); verify `GET /api/settings` via `curl -s http://192.168.0.68:3000/api/settings | jq -r .workgroup` → `TESTWG` and hostname updated
7. Also verify via UI: reload page → General still shows `TESTWG` (values from `useGetApiSettingsQuery`)
8. Restart addon to verify persistence: `ha addons restart local_sambanas2` → wait 10s → `curl -s http://192.168.0.68:3000/api/health` 200 → `curl -s http://192.168.0.68:3000/api/settings | jq -r .workgroup` → still `TESTWG`
9. Capture WS/log evidence: `browser_network_requests` shows PUT 200; `ha addons logs local_sambanas2 | tail -40` shows `Settings update` no ERROR

**Assertions:**

- Dirty gates `Apply`/`Reset` correctly (disabled → enabled → disabled after commit/reset)
- `PUT /api/settings` 200 updates DB and survives restart
- UI reflects new values after Apply + reload

Cleanup: restore original: generate JSON `jq -n --arg h "$ORIG_HOST" --arg w "$ORIG_WG" '{hostname:$h, workgroup:$w}'` merged with original `$ORIG` (preserve other fields) → `curl -X PUT http://192.168.0.68:3000/api/settings -H "Content-Type: application/json" -d "$PAYLOAD"` → 200; verify `GET` returns `ORIG_WG` again
2. Verify `false` boolean round-trip not dropped: set `local_master:false` or `compatibility_mode:false` via PUT, then `curl -s /api/settings | jq .local_master` → `false` (field present, not omitted via `omitempty` bug)
3. Check logs after cleanup restart (optional): no `FATAL`, no `permission denied`
4. Verify bottom bar hidden for `App Configuration` still holds after save flow (navigate to that panel)
5. Record deviations if hostname fetch via `GET /api/hostname` button behaved differently
