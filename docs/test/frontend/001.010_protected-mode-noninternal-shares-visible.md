# Test Case: 001.010_protected-mode-noninternal-shares-visible

## Test Objective

Regression for srat#1303: with addon protection mode ON, non-internal shares that exist and are SMB-accessible (e.g. `usage:media` on an internal path) must remain visible and manageable in the Shares tree — protection blocks *mount* operations, not share management. Hiding them orphans working shares (they cannot be deleted via UI).

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `started`; health 200
2. Protection mode ON: `ha addons info local_sambanas2 | grep -i protected` → `true`
3. Create a media share on an internal path via API (use a `share==null` mount, e.g. `/media` on the system disk):
   ```bash
   MNT=$(curl -s http://192.168.0.68:3000/api/volumes | jq -c '... mount_point_data for /media ...')
   curl -s -X POST http://192.168.0.68:3000/api/share -H "Content-Type: application/json" \
     -d "$(echo "$MNT" | jq --arg n "protvis_$(date +%s)" '{name:$n, mount_point_data:., usage:"media", guest_ok:true, timemachine:false}')" -w "\nHTTP:%{http_code}\n"
   ```
   → 201; record `TEST_SHARE`
4. Confirm SMB-live: `docker exec app_local_sambanas2 smbclient -L //127.0.0.1 -U guest% | grep -i protvis` → listed

**If any preparation step fails** (create not 201, not SMB-visible), **skip**.

## Execution

1. Open Shares tab (`http://localhost:3080/`) → wait 10 s (covers WS live-refresh window)
2. Assert a non-internal group (e.g. `Media Shares`) lists `TEST_SHARE` — absence FAILS the test (the #1303 blind spot)
3. Select `TEST_SHARE` → detail pane renders with Edit affordance (internal-share no-delete rule does NOT apply)
4. Delete `TEST_SHARE` via UI (trash + confirm) → 204; verify gone from `GET /api/shares` and tree

**Assertions:**

- Existing SMB-live non-internal shares render in the tree while protection is ON
- The share is selectable, editable, and deletable via UI (full management, not read-only)
- No console errors on tab load with mixed-usage shares present

## Validation

1. Cleanup fallback: if UI delete was impossible, `DELETE /api/share/$TEST_SHARE` → 204 (record which path worked)
2. Verify baseline: tree back to internal-only shares; `GET /api/shares` has no `protvis_*` residue
3. Check addon logs: no `ERROR`/`panic` correlating with create/delete

**Success criteria:** Non-internal shares visible + manageable in protected mode; cleanup complete; no log errors.
