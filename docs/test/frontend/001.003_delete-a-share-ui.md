# Test Case: 001.003_delete-a-share-ui

## Test Objective

Verify that the frontend UI allows users to delete an existing SMB share via `SharesTreeView` → `ShareActions` menu, that the confirmation dialog is shown, and that the deletion persists via API and `smb.conf`.

## Preparation

1. Ensure the SRAT addon is running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Verify at least one deletable share exists: `curl -s http://192.168.0.68:3000/api/shares | jq -r '.[].name'` — if none, create via `001.001` preparation (use free partition `ata-WD_PC_SN740_SDDPNQD-512G-2006_23482W805056-part2`, `MNT` payload, `histt*` name)
3. Record share to delete: `DEL_SHARE=$(curl -s http://192.168.0.68:3000/api/shares | jq -r '.[] | select(.usage!="internal") | .name' | head -n1)` — prefer a media/backup test share, not an internal system share
4. Ensure frontend is served at `http://localhost:3080/` (via `API_URL=http://192.168.0.68:3000/ SUPERVISOR_URL=http://192.168.0.68/ mise run //frontend:dev:remote`) — page loads with no JS errors
5. Capture baseline: `GET /api/shares` count, `testparm -s | grep -E '^\[.*\]'` count

**If any preparation step fails** (no deletable share, UI not accessible), the test must be **skipped**.

## Execution

1. Navigate to `http://localhost:3080/` → click Shares tab (`#full-width-tab-2`)
2. Expand the group containing `DEL_SHARE` (e.g. `Media Shares`) — set `localStorage["shares.expandedGroups"]` to include `group-media` if needed, or click the TreeItem expander
3. Locate `DEL_SHARE` row in `SharesTreeView` — verify `FolderSharedIcon` and share name visible
4. Open `ShareActions` menu (⋯ `more actions` button) for that row → click **Delete** (or direct Delete button if tree action renders it)
5. Confirmation dialog appears: title `Delete ${DEL_SHARE}?` with acknowledgement checkbox — check `I understand that deleting this share will permanently remove it...` and confirm
6. Wait for UI to reflect deletion — `DEL_SHARE` disappears from `SharesTreeView`, group count decrements, toast/empty state shown if applicable, right panel shows `Select a share from the tree to view details` if deleted share was selected
7. Verify API: `curl -s http://192.168.0.68:3000/api/shares | jq -r '.[].name' | grep -qx "$DEL_SHARE"` should **not** match; `GET /api/shares` length is `baseline-1`
8. Verify `smb.conf` (allow ~5-10 s for async RESTART): `ssh root@192.168.0.68 "docker exec app_local_sambanas2 testparm -s 2>&1 | grep -i \"\[$DEL_SHARE\]\""` should produce no match

**Assertions:**
- Delete confirmation dialog shown and required acknowledgement enforced
- After confirm, `DEL_SHARE` removed from tree without page reload
- `GET /api/shares` no longer contains `DEL_SHARE`
- `testparm -s` no longer contains `[DEL_SHARE]` (uppercased) after soft restart
- Browser console has no uncaught errors; network `DELETE /api/share/${DEL_SHARE}` returns 204

## Validation

1. Verify frontend localStorage cleared if deleted share was selected: `localStorage.getItem("shares.selectedShareKey")` should be `null` or not equal `DEL_SHARE`
2. Check addon logs: `ha addons logs local_sambanas2 --lines 30` — no `ERROR` introduced by delete (expect `INFO ServerProcesses received RESTART` and soft restart logs)
3. Check WS `shares` event: `ws://192.168.0.68:3000/ws` stream contains `event: shares` without `DEL_SHARE` within 5 s (RTK Query tag invalidated)
4. Recreating a share with same `MNT` and name succeeds (`POST /api/share` → 201) — proves delete freed the mount point

**Success criteria:** Share deleted via UI is verifiable through API, `smb.conf`, and WS; UI state, localStorage, and group counts correctly updated; no errors in logs.
