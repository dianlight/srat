# Test Case: 003.010_volume-sensor-repository

## Test Objective

Verify that HA-exposed SRAT volume sensors still resolve their data correctly after the `sensor.py` refactor to `VolumeRepository` selectors: disk sensor attributes mirror `GET /api/volumes` disks, partition sensor attributes mirror the matching partition, and health sensors (`disk_io` / `partition_health`) still expose per-device data. Covers `VolumeRepository.find_disk` / `find_partition` / `find_disk_io` / `find_partition_health` and the `dict(found)` copy behavior in `SRATDiskSensor._find_disk` / `SRATPartitionSensor._find_partition`.

## Preparation

1. Ensure the addon is running and health 200; custom component deployed; HA core logs clean of `custom_components.srat` errors
2. `GET http://localhost:3000/api/volumes` → pick a real disk `D` (id, size, ≥1 partition `P`) and record its fields
3. Confirm the corresponding HA entities exist and are not `unknown`: the SRAT disk sensor for `D`, the SRAT partition sensor for `P`, `sensor.srat_global_disk_health`, and the per-disk IO sensor — via HA states API (`/api/states` filtered to `sensor.srat_*`)

**If any preparation step fails** (no disks, entities missing/`unknown`), the test must be **skipped**.

## Execution

1. Read the disk sensor's `attribute` set for `D`; assert `id` equals `D.id` and `size` equals the `GET /api/volumes` size (repo `find_disk` by `id`)
2. Read the partition sensor's attributes for `P`; assert `id`/`device` match the partition entry in `GET /api/volumes` (`find_partition` across disks)
3. Read the per-disk IO sensor; assert its attributes equal the `disk_io[<device>]` entry of the disk-health data backing `GET /api/volumes` health info (`find_disk_io`); same for the partition health sensor vs `partition_health[<device>]` (`find_partition_health`)
4. Mutation freshness: `POST /filesystem/label`-equivalent is out of scope — instead re-run step 1 after a coordinator refresh (wait for a `volumes` event/`heartbeat`, ≤60 s) and assert attributes are re-derived identically (guards against the `dict(found)` shallow-copy mutating shared coordinator data)

**Assertions:**

- Disk/partition/health sensor attributes match the API data exactly for the sampled entities
- No sensor flips to `unknown` after a refresh cycle
- No `TypeError`/`KeyError` tracebacks referencing `sensor.py` in HA core logs during execution

## Validation

1. Re-read all four sampled entities → still consistent with `GET /api/volumes`
2. HA core logs: no `Traceback` from `custom_components.srat.sensor`; addon logs clean
3. Cleanup: none required (read-only test)

**Success criteria:** all sampled volume sensors resolve identical data before and after a refresh through the `VolumeRepository` selectors, logs clean.
