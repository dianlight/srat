# Test Case: 001.004_shares-legacy-and-history-ui

## Test Objective

Verify the Shares tab hist behaviors: (a) Legacy `HistoryIcon` badge for deprecated standard shares `addons`/`addon_configs`, (b) localStorage persistence of `selectedShareKey`/`expandedGroups` across reload, (c) router `history.state` clearing after `ShareEditDialog` navigation (Volumes→Create Share flow).

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Verify legacy shares exist: `curl -s http://192.168.0.68:3000/api/shares | jq -r '.[] | select(.name=="addons" or .name=="addon_configs") | .name'` → both present with `usage:internal`; `LEGACY_STANDARD_SHARE_NAMES = Set(["addons","addon_configs"])` in `SharesTreeView.tsx`
3. Seed a mounted free partition check (reuse 001.001 free-partition logic) but no share creation required — this case is read-only for hist UI
4. Frontend at `http://localhost:3080/` with `API_URL=http://192.168.0.68:3000/` — clear browser storage then reload to baseline
5. Open devtools — no console errors after initial load

**If any preparation step fails** (legacy shares missing, UI not reachable), **skip** and document (legacy shares require `standard_share_names` config).

## Execution

1. **Legacy badge (hist):** Navigate to Shares tab (`#full-width-tab-2`) → expand `Internal Shares (9)` group (TreeItem `group-internal`). Locate rows `addons` and `addon_configs`:
   - Each row must show `Chip` with `HistoryIcon` (testId `shares-legacy-badge`) and label `Legacy` (data-testid registered in `testIds.ts` → `shares.legacyBadge: "shares-legacy-badge"`)
   - Tooltip on `FolderSharedIcon` for legacy shares should **not** show error (status.is_valid true despite `mount_point_data.invalid==true` for those internal mounts)
   - Assertion: `within(row).getByTestId("shares-legacy-badge")` exists for both legacy rows, absent for non-legacy rows (e.g. `config`)
2. **localStorage persistence:** Select a share (e.g. `media` or `Carola` if media) → verify `localStorage["shares.selectedShareKey"]` set to that shareKey. Expand `Internal Shares` and `Media Shares` → `localStorage["shares.expandedGroups"]` contains `["group-internal","group-media"]` (JSON array). Reload page (`location.reload()`) → shares remain selected and groups stay expanded (hydrate from localStorage in `Shares.tsx:52,59`). Then clear selection → verify key removed.
3. **Router history clearing:** From Volumes tab, select a partition with `share==null` (e.g. `ata-WD_PC_SN740_SDDPNQD-512G-2006_23482W805056-part2`) → click `CREATE SHARE` (navigates to Shares with `location.state.newShareData` and `history.replaceState({})` clearing). Verify `ShareEditDialog` opens with `org_name:""` sentinel and suggested name (uppercased basename). Close dialog without saving → `history.state` is `{}` (`navigate(path,{replace:true, state:{}})` in `Shares.tsx:202`), so refresh does **not** reopen dialog. Also test existing share edit: select a share → trigger edit via `ShareDetailsPanel` → dialog opens via state, close → state cleared.

**Assertions:**
- Legacy `HistoryIcon`/`Legacy` chip present only for `addons`/`addon_configs` (2/9 internal rows), with `data-testid="shares-legacy-badge"`
- Selecting a share persists `selectedShareKey`; expanding groups persists `expandedGroups`; both survive reload and clear correctly
- `ShareEditDialog` history state cleared via `replace:true` after open — reload does not reopen dialog (no infinite open loop)
- Network `GET /api/shares` returns 200; WS indicator green; no `srat/registered-test-id` lint error for the new testId
