# Test Case: 004.003_edit-user-ui

## Test Objective

Verify EDIT USER via UI: selecting a user → `UserDetailsPanel` shows details → `EditIcon` toggles inline `UserEditForm` → change password and share assignments → `Save Changes` → `PUT /user/{username}` (or `PUT /useradmin` for admin) → toast → details update and `smbclient` verifies new password.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Ensure test user exists: `TEST_USER="u$(date +%s | tail -c 6)"` if not already from 004.002; `TEST_PASS="Aa$(date +%s | tail -c 5)!"`; if missing create via `POST /api/user` with `is_admin:false` and one RW share
3. Ensure at least two shares for assignment cross-check: `curl -s http://192.168.0.68:3000/api/shares | jq -r '.[].name' | head -n2` → `SHARE_A`, `SHARE_B` (fallback to one if only one exists)
4. Frontend at `http://localhost:3080/` → Users tab → tree shows `TEST_USER` in `group-users` (or `admin` for admin path); `localStorage["users.expandedGroups"]` contains group
5. Record baseline GET: `curl -s http://192.168.0.68:3000/api/users | jq --arg u "$TEST_USER" '.[] | select(.username==$u)'`

**If any step fails** (no test user, no shares), skip.

## Execution

1. Navigate `http://localhost:3080/` → Users → expand `group-users` → click `TEST_USER` → verify `UserDetailsPanel` shows `Edit` (`getByLabelText` EditIcon) and `Delete` buttons, plus current shares chips
2. Click `Edit` → inline `UserEditForm` appears (`UserEditForm` inside `UserDetailsPanel` children); verify fields: `Username` readOnly (for non-admin existing user) with helper `Username cannot be changed`, `Password`/`Repeat Password` empty, RW/RO Autocompletes populated with `availableShares` (from `GET /api/shares` filtered `!disabled`)
3. Test cross-field validation: type `foo` in Password but different in Repeat → error `Passwords do not match` blocks submit; fix to matching new password `NEW_PASS="Bb$(date +%s | tail -c 5)!"` → error clears
4. Modify shares: RW `Autocomplete` → remove existing if any, add `SHARE_B`; RO add `SHARE_A` if distinct (verify `getOptionDisabled` prevents same share in both); check deduplication logic (`uniqueRwShares`/`uniqueRoShares` filtering)
5. Submit: click `Save Changes` (`type="submit"`, disabled when `!isDirty` then enabled after change) → verify network `PUT /api/user/$TEST_USER` → 200 with updated `rw_shares`/`ro_shares`; toast `User $TEST_USER updated successfully`
6. Verify UI updates: `UserDetailsPanel` exits edit mode (`isEditing=false`), details now show updated shares; `GET /api/users` → `rw_shares` contains `SHARE_B`
7. Verify Samba password: `smbclient -L //127.0.0.1 -U $TEST_USER%$NEW_PASS` → OK (shares listed); old pass `smbclient -L //127.0.0.1 -U $TEST_USER%$TEST_PASS` → `NT_STATUS_LOGON_FAILURE`
8. Admin path (second sub-case if needed): select `admin` → Edit → change `username` allowed (`readOnly=false` when `is_admin:true` with helper `Admin username can be changed`) → PUT `/useradmin` → verify admin rename propagates; revert after test

**Assertions:**
- ReadOnly rules: non-admin username locked, admin username editable; password repeat cross-validation works
- Submit enabled only when `isDirty` and validation passes; API 200 and toast on success
- Samba reflects password change; shares persisted correctly

## Validation

1. Negative: submit empty change without dirty → Save disabled remains; no API call
2. Check logs: `ha addons logs local_sambanas2 | tail -30` and `ha core logs | tail -20` → no ERROR after PUT
3. Verify `testparm -s` still valid after user edit (Samba reload triggered)
4. Cleanup: revert admin name if changed; or delete `TEST_USER` via `DELETE /api/user/$TEST_USER` if this is the final editing test (keep for delete test if next)

**Success criteria:** Inline edit flow works for regular and admin users, validation enforced, backend and Samba verify, no log errors.
