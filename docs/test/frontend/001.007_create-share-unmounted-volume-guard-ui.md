# Test Case: 001.007_create-share-unmounted-volume-guard-ui

## Test Objective

Verify that the Shares-tab create dialog guards against creating a share on an unmounted (or otherwise not write-supported) volume — e.g. any external partition while the addon runs in protection mode (see dianlight/hassio-addons#730). Submitting such a share must either be blocked client-side or surface a clear error; it must not silently create an `is_valid:false` share that spams `Share volume does not exist` warnings in the addon log.

## Preparation

1. Ensure the SRAT addon is running in protection mode: `ha addons info local_sambanas2` → `started`, `protected: true`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Confirm all external partitions are unmounted: `curl -s http://192.168.0.68:3000/api/volumes` → every `/mnt/...` mount point has `is_mounted:false`
3. Ensure frontend is served at `http://localhost:3080/` (via `API_URL=http://192.168.0.68:3000/ SUPERVISOR_URL=http://192.168.0.68/ mise run //frontend:dev:remote`) — page loads with no JS errors
4. Navigate to Shares: `http://localhost:3080/` → click Shares tab (`#full-width-tab-2`)
5. Record baseline share count: `curl -s http://192.168.0.68:3000/api/shares | jq length` → `BASE_COUNT`; snapshot log tail marker: `ha addons logs local_sambanas2 | tail -n 5`

**If any preparation step fails** (addon not in protection mode, UI not accessible), the test must be **skipped**.

## Execution

1. Click Create new share (`#create_new_share`) — `ShareEditDialog` opens
2. Fill Share Name with a valid value, e.g. `ui_guard_test` (pattern `^[a-zA-Z0-9_]+$`)
3. Open the Volume selector — assert every offered option carries the `Read-Only` tag (no write-supported volume exists under protection mode)
4. Select an unmounted external partition (e.g. `ata-WD_PC_SN740_SDDPNQD-512G-2006_23482W805056-part1`)
5. Observe the expected guard (at least one must hold):
   - a) CREATE is disabled while the selected volume is not write-supported, or
   - b) submitting shows a validation/error message naming the unmounted volume and no share is created, or
   - c) submitting creates the share but the UI immediately flags it invalid (error styling/toast) instead of a success toast
6. If a share was created despite the guard missing, record its name (`GUARD_SHARE`) for cleanup

**Assertions:**

- Volume options under protection mode are all tagged `Read-Only`
- No silent success: either submit is blocked, a clear error is shown, or the created share is visibly flagged invalid
- `GET /api/shares` contains no new `is_valid:true` share pointing at an unmounted path
- Browser console has no uncaught errors

## Validation

1. If `GUARD_SHARE` was created: `curl -X DELETE http://192.168.0.68:3000/api/share/${GUARD_SHARE}` → 204; verify `GET /api/shares` length equals `BASE_COUNT`
2. Check addon logs after the flow: `ha addons logs local_sambanas2 | tail -n 30 | grep -c "Share volume does not exist"` → 0 new lines after cleanup (no lingering WARN spam)
3. Check no `ERROR`/`panic` introduced: `ha addons logs local_sambanas2 | tail -n 30 | grep -iE "panic|FATAL"` → empty
4. Leave protection mode ON (restore to OFF only in suite teardown step)

**Success criteria:** The UI never lets an unmounted-volume share pass as a normal success; any created artifact is cleaned up and WARN spam ceases after cleanup.
