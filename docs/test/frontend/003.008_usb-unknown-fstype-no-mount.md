# Test Case: 003.008_usb-unknown-fstype-no-mount

## Test Objective

Verify that a visible partition whose `filesystem_info.type` is empty (unknown) cannot be mounted, that the backend rejects the mount with a clear 4xx error, and that the UI surfaces the failure instead of failing silently. Captures the fstype-detection gap where the OS knows the filesystem (e.g. `blkid` reports ext4) but `/api/volumes` reports `""`.

## Preparation

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `state: started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Find a partition with unknown fstype (generalized — USB `sdc1` is the known example):
   ```bash
   curl -s http://192.168.0.68:3000/api/volumes | jq -r '.[] | .partitions | to_entries[] | select(.value.filesystem_info.type == "") | "\(.key)\t\(.value.size)\t\(.value.legacy_device_path)"'
   ```
   - If none exists, this case must be **skipped** (no unknown-fstype partition present).
   - Export: `export TEST_PARTITION_ID=<partition-id>` (e.g. `usb-General_USB_Flash_Disk_0111607137301461-0:0-part1`).
3. Record OS ground truth for that device (both namespaces agree on blkid):
   ```bash
   ssh root@192.168.0.68 -p 22222 "blkid /dev/sdc1; lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINT,UUID | grep -E 'sdc1|sdc'"
   ssh root@192.168.0.68 -p 22 "docker exec app_local_sambanas2 blkid /dev/sdc1"
   ```
   - Known anomaly (2026-09-04): host AND container `blkid` both report `/dev/sdc1: UUID="bd1baeb0-..." TYPE="ext4"`, `lsblk` shows `sdc1 57.6G ext4` unmounted, while `/api/volumes` reports `filesystem_info.type:""`, `support.canMount:false`.
4. Record the partition's `support` flags: `... | .filesystem_info.support` (expect `canMount:false`, `isExportable:false`, `canFormat:true` in the anomaly case).
5. Ensure frontend is served at `http://localhost:3080/` via `mise run //frontend:dev:remote` (`API_URL=http://192.168.0.68:3000/`).

**If any preparation step fails** (addon not running, API unreachable, no unknown-fstype partition), the test must be **skipped**.

## Execution

1. Attempt the mount via API (expected rejection — read-only in effect, no mount is created):
   ```bash
   curl -s -X POST http://192.168.0.68:3000/api/volume/mount -H "Content-Type: application/json" \
     -d "{\"path\":\"/mnt/<sanitized-$TEST_PARTITION_ID>\",\"root\":\"/\",\"flags\":[],\"custom_flags\":[],\"is_mounted\":false,\"is_to_mount_at_startup\":false,\"type\":\"ADDON\",\"device_id\":\"$TEST_PARTITION_ID\"}" -w "\nHTTP %{http_code}\n"
   ```
   → record status and body (known: `404 {"detail":"Device Not Found"}` on 2026-09-04).
2. Query filesystem state:
   ```bash
   curl -s "http://192.168.0.68:3000/api/filesystem/state?partition_id=$TEST_PARTITION_ID" -w "\nHTTP %{http_code}\n"
   ```
   → record status and body (known: `400 {"detail":"Partition has no filesystem type"}`).
3. UI check: open Volumes tab → select the partition → observe the detail panel:
   - Note whether a MOUNT action is offered (`getPartitionActionItems` does not gate on `canMount`, so it may be offered) and, if clicked, assert a visible error (toast/banner) appears — a silent no-op is a FAIL.
   - Take a screenshot of the detail panel; note the missing fstype label in the tree row (e.g. `62 GB` with no `ext4` tag vs siblings).
4. Confirm no mount was created: re-fetch the partition from `/api/volumes` — `mount_point_data` must still be `{}` and container `mount | grep <device>` empty.

**Assertions:**

- `POST /api/volume/mount` for the unknown-fstype partition returns 4xx (not 2xx) with a filesystem-related reason.
- `GET /api/filesystem/state?partition_id=...` returns 4xx naming the missing filesystem type.
- Host/container `blkid` output and the API `filesystem_info.type` are both recorded, exposing any detection gap.
- UI does not silently swallow the failure (error surfaced or action withheld with explanation).
- No mount side effects were created by the probes.

## Validation

1. Check addon logs (`docker logs app_local_sambanas2 --tail 20`) for the 4xx lines — expected, but no `panic`/`FATAL` and no `permission denied` for the data directory.
2. Re-fetch `/api/volumes` for the partition — `filesystem_info.type` still `""`, `mount_point_data` still `{}` (unchanged).
3. File/update a bug with the `blkid`-vs-API evidence when the OS knows the fstype but the API reports `""`.

**Success criteria:** The unknown-fstype mount block is verified end-to-end (API rejection + UI behavior), the fstype-detection gap is evidenced with `blkid`/`lsblk` output, and no state was mutated.
