# Test Case: 003.005_format-partition-label-and-mount

## Test Objective

Verify that after formatting a data partition with a new label, the new label appears in the Volumes tree and the partition is mountable without errors.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `state: started`; `curl -s http://192.168.0.68:3000/api/health` → 200 with `alive:true`
2. Target partition (destructive — confirmed by user): `TEST_PARTITION_ID=ata-WD_PC_SN740_SDDPNQD-512G-2006_23482W805056-part1` (`/mnt/ata-WD_PC_SN740_SDDPNQD-512G-2006_23482W805056-part1`, `system:false`, non-system data partition)
3. Format params: `TEST_FSTYPE=ext4`, `TEST_LABEL=SRATFMT02` (satisfies ext4 `labelRule ^[^\x00/]{1,16}$`; distinct from previous `Test123`)
4. Verify partition is format-capable: `curl -s "http://192.168.0.68:3000/api/filesystem/support?fstype=ext4" | jq .canFormat` → `true`
5. Frontend at `http://localhost:3080/` via `API_URL=http://192.168.0.68:3000/ SUPERVISOR_URL=http://192.168.0.68/ mise run //frontend:dev:remote` → `bun tsc --noEmit` green, WS `ws://192.168.0.68:3000/ws` reachable
6. Format action is gated on unmounted state (`PartitionActionItems.ts:161-171` — `Format Partition` only when `!isMounted`); ensure partition is unmounted before format (via UI UNMOUNT or `POST /api/volume/unmount`). If a share is attached (`share != null`), delete it first.
7. Record baseline label: `curl -s http://192.168.0.68:3000/api/volumes | jq --arg pid "$TEST_PARTITION_ID" '.[] | select(.partitions[$pid]!=null) | .partitions[$pid] | {name, fs_type}'`

**If any preparation step fails**, skip and document.

## Execution

1. Navigate `http://localhost:3080/` → click `VOLUMES` tab → expand disk `WD PC SN740` → select `$TEST_PARTITION_ID`. Confirm detail panel shows `Not Mounted` and Actions contain `Format Partition` (MUI `colorError`).
2. Click `Format Partition` → dialog `Format Partition: <label>` opens. Select `Filesystem type=ext4`, enter `Label=$TEST_LABEL`, leave `Force=false`, `Verbose=true` (to capture logs). Click `Format` → toast `Format operation started`, dialog shows progress + live logs.
3. Wait for `filesystem_task` WS event `operation:format status:success` (or dialog `success` alert). Format is async — poll up to 120s.
4. Verify new label via API: `curl -s http://192.168.0.68:3000/api/volumes | jq --arg pid "$TEST_PARTITION_ID" '.[] | select(.partitions[$pid]!=null) | .partitions[$pid] | {name, fs_type}'` → `name==$TEST_LABEL`, `fs_type==ext4`. Also `GET /filesystem/label?partition_id=$TEST_PARTITION_ID` → `{"label": $TEST_LABEL}`.
5. Verify Volumes tree shows new label: re-select partition in UI, tree node/detail header shows `$TEST_LABEL` (screenshot).
6. Mount the partition: click `Mount Partition` (or `POST /api/volume/mount` with stored `mountPointData`) → detail shows `Mounted`, `Mount Point /mnt/$TEST_PARTITION_ID`.
7. Verify mount via API: `curl -s http://192.168.0.68:3000/api/volumes | jq --arg pid "$TEST_PARTITION_ID" '.[] | select(.partitions[$pid]!=null) | .partitions[$pid].mount_point_data | to_entries[0].value | {is_mounted, path, fstype}'` → `is_mounted:true`. Host check `lsblk -o NAME,MOUNTPOINT,FSTYPE,LABEL | grep sdd1` shows mountpoint + `LABEL=$TEST_LABEL`.
8. Write/read smoke (optional, no credentials needed — direct FS): `docker exec addon_local_sambanas2 sh -c "echo hello > /mnt/$TEST_PARTITION_ID/.srat_fmt_test && cat /mnt/$TEST_PARTITION_ID/.srat_fmt_test && rm /mnt/$TEST_PARTITION_ID/.srat_fmt_test"` → `hello` with no I/O error.

**Assertions:**

- Format task completes with `status:success`, no `failure` message
- `GET /api/volumes` partition `name` equals new label, `fs_type` equals requested fstype
- Volumes tree/detail displays new label (screenshot evidence)
- Mount succeeds after format with `is_mounted:true`, no `ERROR` in addon logs for mount
- FS write/read round-trip succeeds without errors

## Validation

1. WS freshness: `volumes` event payload after format and after mount matches concurrent REST `/api/volumes` within 2s (see #971 class).
2. Logs: `ha addons logs local_sambanas2` tail → no `ERROR/panic` for format/mount; `ha core logs` → no `custom_components.srat` tracebacks.
3. Leave partition mounted with new label (per test objective — do not revert label). Record final state in evidence.
4. Restore lab mode / settings unchanged; leave no test shares behind.

**Success criteria:** New label visible in Volumes tree after format; partition mounts cleanly with no errors; API, WS, and UI agree on label + mount state.

## Findings

Ran 2026-09-04, addon `local_sambanas2` 2026.8.0-rc13 (live binary, no rebuild), `TEST_PARTITION_ID=ata-WD_PC_SN740_SDDPNQD-512G-2006_23482W805056-part1`, `TEST_FSTYPE=ext4`, `TEST_LABEL=SRATFMT02` (user chose "new label" without specifying a string — SRATFMT02 selected by agent).

- **PASS** — unmount via `DELETE /api/volume` → 204, `is_mounted` false.
- **PASS** — format via `POST /api/filesystem/format` → 200 `Format operation started`; `filesystem_service.go:687 Format operation completed successfully`; `GET /filesystem/label` → `SRATFMT02`; container `blkid`/`lsblk` → `sdd1 ext4 SRATFMT02`; state clean.
- **PASS** — mount via `POST /api/volume/mount` → 200 `is_mounted:true, is_write_supported:true`; container write/read smoke (`hello-srat` round-trip) OK; post-restart mount logged `volume_mount_manager.go:106 Successfully mounted volume`.
- **BUG [#1063]** — `GET /api/volumes` partition `name` stayed `Test123` for 120s+ after format (while `mount_point_data.disk_label` already `SRATFMT02`); Volumes tree showed `Test123 ... Mounted`. After addon restart (cache clear), `name` → `SRATFMT02` and tree shows `SRATFMT02 ... Mounted`. `volume_service.go:931 Refreshing volume cache after successful format task` fires but does not update the DiskMap name. REST-level staleness (distinct from #971 WS-only class). Suggested fix: set `DiskMap` partition `Name = req.Label` after format (as `SetPartitionLabel` does) + emit disk update.
- **NOTE** — UI tree node click not automatable (MUI TreeView exposes no accessible node names to the snapshot); state changes done via API, tree verified via snapshot text + screenshots.
- **NOTE** — one `api/ws.go:294 Failed to upgrade connection` ERROR in logs is from the agent's own malformed `curl -H "Connection: Upgrade"` WS probe (missing `Sec-Websocket-Version`), not an app fault.
