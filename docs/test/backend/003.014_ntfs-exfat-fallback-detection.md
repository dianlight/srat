# Test Case: 003.014_ntfs-exfat-fallback-detection

## Test Objective

Verify that filesystem type detection resolves NTFS and exFAT partitions through the adapter signature table when the kernel magic probe cannot (issue #1513, PR #1514): the hardware→DTO mount point data must carry a resolved fstype (`ntfs`/`ntfs3` for NTFS, `exfat` for exFAT) so these partitions can be mounted, checked, and shared instead of staying with an empty fstype.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `state: started`; `curl -s http://192.168.0.68:3000/api/health` → 200 with `alive:true`
2. Target partitions: an NTFS (`sdc1`, label `SRATNTFS01`) and/or exFAT (`sdb2`) spare data partition (`system:false`) with a known-good filesystem, unmounted. If a partition is missing, confirm with the user and format it via `POST /api/filesystem/format` with `fstype` `ntfs` or `exfat` before continuing. Do not format without user approval.
3. For each candidate, set `TEST_DEVICE_NAME` to its Supervisor device name (for example `sdb2`) and confirm that its hardware entry has no `ID_FS_TYPE`:
   ```bash
   docker exec -e TEST_DEVICE_NAME="$TEST_DEVICE_NAME" app_local_sambanas2 sh -c 'curl -s http://supervisor/hardware/info -H "Authorization: Bearer $SUPERVISOR_TOKEN" | jq -r --arg name "$TEST_DEVICE_NAME" ".data.devices[] | select(.name == \$name) | .attributes[\"ID_FS_TYPE\"] // \"<missing>\""'
   ```
   → `<missing>` or an empty value. If every candidate already reports an `ID_FS_TYPE`, skip this case: the fallback path would not be exercised.
4. Ensure partitions are unmounted before mount steps (via UI UNMOUNT or `DELETE /api/volume?mount_path=<path>`). Delete any attached test shares first.

**If any preparation step fails** (no agreed spare partition, user declines format, addon not running), the test must be **skipped**.

## Execution

1. Fetch volumes for the prepared partition whose Supervisor hardware entry has no `ID_FS_TYPE`:
   ```bash
   curl -s http://192.168.0.68:3000/api/volumes | jq -r --arg id "$TEST_PARTITION_ID" '.[] | .partitions | to_entries[] | select(.key == $id) | "\(.key)\t\(.value.mount_point_data[0].fstype // "<empty>")"'
   ```
2. For each prepared NTFS/exFAT partition, assert the reported fstype is resolved (NTFS → `ntfs`/`ntfs3`; exFAT → `exfat`) and no partition is left with an empty fstype. Because the Supervisor entry has no `ID_FS_TYPE` and the kernel magic probe cannot identify NTFS/exFAT, a resolved type proves the adapter signature probe supplied it. With debug logging enabled, also confirm the probe path in the addon log:
   ```bash
   ha addons logs local_sambanas2 | grep -F "Recovered missing fstype via FS probe"
   ```
   → a line naming the target device path and the expected fstype. If debug logging is not enabled, set the addon option `log_level=debug`, restart the addon, and repeat step 1 before continuing.
3. Mount an unmounted NTFS/exFAT partition with empty flags:
   ```bash
   curl -s -X POST http://192.168.0.68:3000/api/volume/mount -H "Content-Type: application/json" -d "{\"partitionId\":\"$TEST_PARTITION_ID\",\"mountPointData\":{\"path\":\"/mnt/$TEST_PARTITION_ID\",\"fstype\":null,\"flags\":{},\"custom_flags\":{}},\"force\":false,\"verbose\":true}"
   ```
   → 200, `is_mounted:true`.
4. Verify OS-level fstype agreement by matching the exact mount-point field in `/proc/mounts`, so a mount for `part10` cannot satisfy a request for `part1`:
   ```bash
   docker exec app_local_sambanas2 awk -v mount_point="/mnt/$TEST_PARTITION_ID" '$2 == mount_point { print $3; exit }' /proc/mounts
   ```
   → exactly `ntfs3`/`fuseblk` for NTFS or `exfat` for exFAT.

**Assertions:**

- NTFS and exFAT partitions resolve a fstype through the adapter signature probe (no empty fstype on the fallback path)
- Mount with empty flags succeeds and OS mount reports the expected fstype
- `GET /api/volumes` agrees with `/proc/mounts` on fstype and mount state

## Validation

1. Write smoke (direct FS): `docker exec app_local_sambanas2 sh -c "echo hello > /mnt/$TEST_PARTITION_ID/.srat_ntfs_exfat_test && cat /mnt/$TEST_PARTITION_ID/.srat_ntfs_exfat_test && rm /mnt/$TEST_PARTITION_ID/.srat_ntfs_exfat_test"` → `hello` with no I/O error.
2. Logs: `ha addons logs local_sambanas2` tail → no `ERROR/panic` for fstype detection or mount; `ha core logs` → no `custom_components.srat` tracebacks.
3. Cleanup: delete the test share if created; unmount the partition via `DELETE /api/volume?mount_path=<path>` and record final state.

**Success criteria:** NTFS and exFAT partitions are detected with the correct fstype via the adapter-aware fallback and can be mounted; the empty-fstype mount block for these filesystems is gone.
