# Test Case: 003.022_addon-mount-automount-rw-share-external-write

## Test Objective

Verify the full addon-owned path: mount a volume with SRAT, enable automount, create a share assigned to a read/write user, and confirm an external SMB client authenticated as that user can see and write to the share.

## Preparation

> Status note: an earlier run failed at execution step 1 because the mount payload omitted `fstype`, which makes the helper use `auto` detection and fail with `no suitable filesystem` on exFAT volumes. The payload now passes the filesystem type reported by the volumes API.

These steps assume protection mode is **off**. Confirm it from inside the addon with `curl -s http://supervisor/addons/local_sambanas2/info -H "Authorization: Bearer $SUPERVISOR_TOKEN" | jq '.data.protected'` → `false`. If it is `true`, set it to `false` with `POST http://supervisor/addons/local_sambanas2/security` and body `{"protected":false}`, restart the addon, recreate the port `3000` forward, and confirm `GET /api/problems` does not contain `protected_mode`.

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `started`; `curl -s -o /dev/null -w '%{http_code}' http://192.168.0.68:3000/api/health` → `200`.
2. Confirm the Samba port is reachable from the test host: `nc -z 192.168.0.68 445` → exit `0`.
3. Choose a mountable partition owned by the addon. Write support is only meaningful **after** mounting, so do not require `is_write_supported:true` in this pre-mount selection; the check happens in execution step 1. Record `PART_ID`, `MNT_PATH`, and the current automount, mount, and share state for cleanup:
   ```bash
   curl -s http://192.168.0.68:3000/api/volumes | jq -c '
     [ .[] as $disk | $disk.partitions[]? | .mount_point_data // {} | to_entries[]
       | select(.value.path | startswith("/mnt/"))
       | select((.value.is_ha_mounted // false) == false)
       | select((.value.fstype // "") | test("^(ext4|xfs|vfat|exfat|ntfs3|btrfs|f2fs)$"))
       | .value ] | first'
   ```
   The result must be non-null; save its `device_id` as `PART_ID`, `path` as `MNT_PATH`, and `fstype` as `FSTYPE`. Prefer a candidate with `share == null`; if none exists, record its existing share name and leave that share untouched. Avoid HA OS system partitions such as `hassos-boot`.
4. Generate unique test names: `export TS=$(date +%s)`, `TEST_SHARE="rwtest-$TS"`, `TEST_USER="rwu$(printf %s "$TS" | tail -c 5)"`, `TEST_PASS="RwTest${TS: -4}!"`.
5. Confirm no leftovers: `curl -s http://192.168.0.68:3000/api/users | jq -r --arg u "$TEST_USER" '.[] | select(.username==$u) | .username'` → empty; `curl -s http://192.168.0.68:3000/api/shares | jq -r --arg s "$TEST_SHARE" '.[] | select(.name==$s) | .name'` → empty.

**If any preparation step fails** (addon unavailable, no mountable addon-owned partition, SMB port closed, leftovers present), the test must be **skipped** and documented.

## Execution

1. Mount the chosen partition with SRAT when it is not already mounted:

   ```bash
   curl -s -X POST http://192.168.0.68:3000/api/volume/mount \
     -H 'Content-Type: application/json' \
     -d "{\"path\":\"$MNT_PATH\",\"root\":\"/\",\"fstype\":\"$FSTYPE\",\"flags\":[],\"custom_flags\":[],\"is_mounted\":false,\"is_to_mount_at_startup\":false,\"type\":\"ADDON\",\"device_id\":\"$PART_ID\"}" \
     -w "\nHTTP:%{http_code}\n"
   ```

   Expect `HTTP:200`; `GET /api/volumes` shows `is_mounted:true`, `invalid:false`, and `is_write_supported:true` for `PART_ID`. If the mount succeeds but the volume is still read-only or invalid, this environment cannot provide a writable addon mount: mark the case **SKIP** with the API evidence and stop; do not force the remaining steps.

2. Enable automount for that mount point:

   ```bash
   curl -s -X PATCH http://192.168.0.68:3000/api/volume/settings \
     -H 'Content-Type: application/json' \
     -d "{\"path\":\"$MNT_PATH\",\"root\":\"/\",\"type\":\"ADDON\",\"is_mounted\":true,\"is_to_mount_at_startup\":true}" \
     -w "\nHTTP:%{http_code}\n"
   ```

   Expect `HTTP:200`; `GET /api/volumes` shows `is_to_mount_at_startup:true`.

3. Create the Samba user:

   ```bash
   curl -s -X POST http://192.168.0.68:3000/api/user \
     -H 'Content-Type: application/json' \
     -d "{\"username\":\"$TEST_USER\",\"password\":\"$TEST_PASS\",\"is_admin\":false}" \
     -w "\nHTTP:%{http_code}\n"
   ```

   Expect `HTTP:201`.

4. Create the share on the mounted addon path:

   ```bash
   curl -s -X POST http://192.168.0.68:3000/api/share \
     -H 'Content-Type: application/json' \
     -d "{\"name\":\"$TEST_SHARE\",\"usage\":\"media\",\"guest_ok\":false,\"mount_point_data\":{\"path\":\"$MNT_PATH\",\"root\":\"/\",\"type\":\"ADDON\",\"device_id\":\"$PART_ID\",\"is_mounted\":true,\"fstype\":\"$FSTYPE\"}}" \
     -w "\nHTTP:%{http_code}\n"
   ```

   Expect `HTTP:201`; `GET /api/shares` shows the share with `status.is_valid:true`.

5. Assign the user as read/write on that share:

   ```bash
   curl -s -X PUT "http://192.168.0.68:3000/api/user/$TEST_USER" \
     -H 'Content-Type: application/json' \
     -d "{\"username\":\"$TEST_USER\",\"rw_shares\":[\"$TEST_SHARE\"]}" \
     -w "\nHTTP:%{http_code}\n"
   ```

   Expect `HTTP:200`; `GET /api/users` shows `rw_shares` containing `TEST_SHARE`.

6. Wait 12 s for the asynchronous Samba soft restart, then verify the generated config:

   ```bash
   sleep 12
   ssh root@192.168.0.68 "docker exec app_local_sambanas2 testparm -s 2>&1" \
     | grep -i -A8 "\[$TEST_SHARE\]"
   ```

   Assertions on the share section: `writeable = yes`, the `valid users` line contains the HA mount account followed by `$TEST_USER`, no `read list` line, no `read only` line.

7. Write and read back from an external SMB client (this host, not inside the addon):
   ```bash
   printf 'srat-rw-%s\n' "$TS" > /tmp/srat-rw-src.txt
   smbclient "//192.168.0.68/$TEST_SHARE" -U "$TEST_USER%$TEST_PASS" \
     -c "put /tmp/srat-rw-src.txt srat-rw-$TS.txt; get srat-rw-$TS.txt /tmp/srat-rw-back.txt; ls"
   cmp -s /tmp/srat-rw-src.txt /tmp/srat-rw-back.txt && echo ROUNDTRIP_OK
   ```
   Assertions: `smbclient` exits `0`, output contains no `NT_STATUS_` error, `ls` lists `srat-rw-$TS.txt`, and `ROUNDTRIP_OK` is printed.

**Assertions:**

- Mount 200, automount patch 200, user create 201, share create 201, user update 200
- Share `status.is_valid:true` and present in `smb.conf` with `writeable = yes`
- Configured read/write user is in `valid users` and absent from `read list`
- External SMB client writes and reads back the same bytes as that user

## Validation

1. Verify authentication is enforced: `smbclient "//192.168.0.68/$TEST_SHARE" -U "$TEST_USER%WrongPass" -c ls` → `NT_STATUS_LOGON_FAILURE`.
2. Check addon logs: `ha apps logs local_sambanas2 | tail -50 | grep -iE "ERROR|panic|FATAL"` → no new errors tied to this run.
3. Clean up in order:
   - `smbclient "//192.168.0.68/$TEST_SHARE" -U "$TEST_USER%$TEST_PASS" -c "rm srat-rw-$TS.txt"`
   - `curl -X DELETE http://192.168.0.68:3000/api/user/$TEST_USER` → `200`/`204`
   - `curl -X DELETE http://192.168.0.68:3000/api/share/$TEST_SHARE` → `200`/`204`
   - Restore automount with `PATCH /api/volume/settings` using the value recorded in preparation
   - If the partition was unmounted initially: `curl -X DELETE "http://192.168.0.68:3000/api/volume?mount_path=$MNT_PATH"` → `200`
4. Re-check `GET /api/shares` and `GET /api/users` no longer contain the test entries.

> Known log noise: a `supervisor_service.go` `Mounting error ... mount_activation_error` may appear when a share is created. It is environment-specific, does not affect SMB export or writes, and does not fail this case.

**Success criteria:** All assertions pass, wrong-password access is rejected, and cleanup restores the baseline state.
