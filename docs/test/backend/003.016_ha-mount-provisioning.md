# Test Case: 003.016_ha-mount-provisioning

## Test Objective

Verify SRAT can provision and remove an HA-managed `disk` mount through the Supervisor API (`POST /mounts` / `DELETE /mounts/{name}`) and that the resulting mount is tracked with an ownership marker (`ha_mount_name`).

> Status note: this capability is not implemented yet (change 055 task group 4 is unchecked; `dto.MountPointData.HaMountName` and the create/remove flow do not exist). The case is expected to **fail** until it lands; it is a tracking test, not a validation of shipped behavior.

## Preparation

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `started`; health 200
2. Confirm the Supervisor mount API accepts `disk` mounts: `ha mounts add --help` shows `--type disk`
3. Pick an unused, non-system partition (not `/dev/sda*`, not an LVM member) from `GET /api/volumes`; note `PART_ID` and its filesystem UUID

**If any preparation step fails**, the test must be **skipped**.

## Execution

1. `POST /api/volume/mount` with the partition and an HA backend request (name + usage `media`/`share`/`backup`) → expect 2xx
2. `ha mounts info --raw-json` → assert the new mount appears with `type: disk` and a `user_path`
3. `GET /api/volumes` → assert the partition is mounted and its `mount_point_data` carries `ha_mount_name` equal to the created mount name
4. `DELETE /api/volume` (unmount) → expect 2xx and assert the Supervisor mount is removed from `ha mounts info`
5. `GET /api/volumes` → assert the local mount row is gone

**Assertions:**

- Create/remove both succeed through SRAT (not via `ha mounts add`)
- `ha_mount_name` recorded on create and cleared on remove
- No orphaned Supervisor mount after SRAT removal

## Validation

1. `ha mounts info` shows no leftover test mount
2. Addon logs show no panic/ERROR from the provisioning flow

**Success criteria:** SRAT provisions and removes a disk mount end-to-end, tracking ownership; cleanup leaves no Supervisor mount.
