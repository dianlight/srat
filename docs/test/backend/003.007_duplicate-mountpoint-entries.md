# Test Case: 003.007_duplicate-mountpoint-entries

## Test Objective

Detect duplicate `mount_point_data` entries for a single partition (e.g. live path plus a stale orphan from a mountpoint sanitization change) and verify the UI does not silently lose all partition actions as a result.

## Preparation

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `state: started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Determine the test partition (generalized — WD part2 is the known example, not required):
   ```bash
   curl -s http://192.168.0.68:3000/api/volumes | jq -r '.[] | .partitions | to_entries[] | "\(.key)\t\(.value.mount_point_data | length)"' | column -t
   ```
   - Prefer a partition with `mount_point_data | length > 1` if one exists; otherwise use a normally-mounted partition (`length == 1`) as the control case.
   - Export: `export TEST_PARTITION_ID=<partition-id>`
3. Record OS ground truth (container mount namespace — host namespace may differ):
   ```bash
   ssh root@192.168.0.68 -p 22 "docker exec app_local_sambanas2 sh -c 'mount | grep -E \"sdd2|/mnt/ata|sdc1\"; ls -ld /mnt/*'"
   ```
4. Take a `dmesg | tail -1` baseline on the host for rescan-spam correlation.
5. Ensure frontend is served at `http://localhost:3080/` via `mise run //frontend:dev:remote` (`API_URL=http://192.168.0.68:3000/`).

**If any preparation step fails** (addon not running, API unreachable), the test must be **skipped**.

## Execution

1. Fetch the partition entry:
   ```bash
   curl -s http://192.168.0.68:3000/api/volumes | jq --arg pid "$TEST_PARTITION_ID" '.[] | select(.partitions[$pid]!=null) | .partitions[$pid]'
   ```
2. Count `mount_point_data` keys: `... | .mount_point_data | length` → record the count and every key path.
3. For each mount entry, record `{path, is_mounted, is_to_mount_at_startup, invalid, is_write_supported, share.name}`.
   - Known anomaly pattern (WD part2, 2026-09-04): dashes path `/mnt/ata-WD_...-part2` with `is_mounted:false(absent per #1009)`, `invalid:true`, `is_to_mount_at_startup:false` alongside underscores path `/mnt/ata_WD_..._part2` with `is_mounted:true`, `share:{name:sdd2}`.
4. Verify OS state: at most ONE of the listed paths is an active mount in the container (`mount | grep <path>`); any other entry is a stale orphan (assert `invalid:true` or `is_mounted:false` on orphans).
5. Verify UI: open Volumes tab, expand the disk, confirm the tree shows `N mountpoint(s)` with N matching the API count; select the partition and assert the detail Actions row state:
   - With current `PartitionActionItems.ts:55-62` (`mount_point_data length > 1 → return null`), a duplicate yields NO action buttons (not even the small-screen `more actions` button) — record this as the observed behavior.

**Assertions:**

- API `GET /api/volumes` returns 200 and the partition entry is present.
- Reported `mount_point_data` count matches the UI `N mountpoint(s)` label.
- No more than one listed path is actively mounted at OS level.
- Any non-mounted duplicate entry is identifiable as stale (`invalid:true` and/or `is_mounted:false` with no OS mount).
- UI action-row state is recorded (present vs null) for the duplicate case.

## Validation

1. No state was mutated by this case (read-only): re-fetch `GET /api/volumes` for the partition and diff against step 1 — must be identical.
2. Check addon logs (`docker logs app_local_sambanas2 --tail 20`) — no `ERROR`/`panic` introduced by read-only probes.
3. `dmesg` diff vs baseline → note any `sdc: sdc1`-style rescan spam observed during the run.
4. Do NOT delete the orphan entry as part of this case — file/update a bug with the evidence instead.

**Success criteria:** Duplicate (or control single) mount entries are fully characterized across API, OS, and UI; stale orphans are identifiable; the UI action-row behavior for duplicates is documented with evidence.
