# Test Case: 003.024_ha-to-addon-mount-share-persistence

## Test Objective

Verify that a share with a read/write user survives a change of mount ownership from Home Assistant to the addon: after HA unmounts a volume and SRAT mounts the same device under its own path, the share must remain valid, visible, and writable by its configured read/write user.

> Status note: device-based share re-association and persisted path repair are now implemented in `GetSharesByDeviceID`, `ReassociateShareMount`, the `OnMountPoint` handler, and `enrichSharePartitionFromCache`. An earlier run hit two problems: a device ID containing `:` is not a valid mount path, and omitting `fstype` makes the mount helper use failing automatic detection. Both are corrected below.

## Preparation

These steps assume protection mode is **off**. Confirm it from inside the addon with `curl -s http://supervisor/addons/local_sambanas2/info -H "Authorization: Bearer $SUPERVISOR_TOKEN" | jq '.data.protected'` → `false`. If it is `true`, set it to `false` with `POST http://supervisor/addons/local_sambanas2/security` and body `{"protected":false}`, restart the addon, recreate the port `3000` forward, and confirm `GET /api/problems` does not contain `protected_mode`.

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `started`; health check → `200`.
2. Pick a writable partition not currently mounted. Record `PART_ID`, `DEVICE="/dev/disk/by-id/$PART_ID"`, and its `fstype` from `GET /api/volumes` as `FSTYPE`; verify `test -e "$DEVICE"` → exit `0`.
3. Confirm `ha mounts add --help` supports `--type disk` and `--device`.
4. Generate unique test names: `TS=$(date +%s)`, `TEST_SHARE="hatransfer-$TS"`, `TEST_USER="htu$(printf %s "$TS" | tail -c 5)"`, `TEST_PASS="HaTest${TS: -4}!"`. Confirm no leftovers in `GET /api/users` or `GET /api/shares`.

**If any preparation step fails**, the test must be **skipped**.

## Execution

1. Mount the device through Home Assistant:

   ```bash
   ha mounts add srat_transfer_back --type disk --device "$DEVICE"
   ```

   Expect success; discover the HA path from `GET /api/volumes` filtered by `device_id == $PART_ID` and `is_ha_mounted == true`. Save it as `HA_PATH`. If the API has not surfaced the new HA mount, use `ha mounts info --raw-json | jq -r --arg mount srat_transfer_back '.[] | select(.name==$mount) | .user_path'` as `HA_PATH` and record this fallback as a deviation.

   Samba exports names in uppercase with hyphens replaced by underscores. Use `EXPORTED_NAME=$(printf '%s' "$TEST_SHARE" | tr '[:lower:]-' '[:upper:]_')` for `smbclient` and the `testparm` section lookup. The `smbclient` binary is available inside the addon container; connect to `//192.168.0.68` from there.

2. Create a Samba user, create the share on `HA_PATH`, and assign that user as read/write, using the API sequence from `003.022` steps 3–5:

   ```bash
   curl -s -X POST http://192.168.0.68:3000/api/user \
     -H 'Content-Type: application/json' \
     -d "{\"username\":\"$TEST_USER\",\"password\":\"$TEST_PASS\",\"is_admin\":false}" \
     -w "\nHTTP:%{http_code}\n"
   curl -s -X POST http://192.168.0.68:3000/api/share \
     -H 'Content-Type: application/json' \
     -d "{\"name\":\"$TEST_SHARE\",\"usage\":\"media\",\"guest_ok\":false,\"mount_point_data\":{\"path\":\"$HA_PATH\",\"root\":\"/\",\"type\":\"HOST\",\"device_id\":\"$PART_ID\",\"is_mounted\":true,\"fstype\":\"$FSTYPE\"}}" \
     -w "\nHTTP:%{http_code}\n"
   curl -s -X PUT "http://192.168.0.68:3000/api/user/$TEST_USER" \
     -H 'Content-Type: application/json' \
     -d "{\"username\":\"$TEST_USER\",\"rw_shares\":[\"$TEST_SHARE\"]}" \
     -w "\nHTTP:%{http_code}\n"
   ```

   Expect `HTTP:201` for the share and `HTTP:200` for the assignment. After 12 s, confirm an external write succeeds as `TEST_USER` (baseline from `003.022` step 7).

3. Unmount in Home Assistant, not through SRAT (SRAT returns `409` for HA-owned volumes, see `003.015`):

   ```bash
   ha mounts remove srat_transfer_back
   ```

   `GET /api/volumes` shows no mounted row for `PART_ID`.

4. Mount the same device with SRAT:

   ```bash
   ADDON_PATH="/mnt/$(printf '%s' "$PART_ID" | tr ':' '_')"
   curl -s -X POST http://192.168.0.68:3000/api/volume/mount \
     -H 'Content-Type: application/json' \
     -d "{\"path\":\"$ADDON_PATH\",\"root\":\"/\",\"fstype\":\"$FSTYPE\",\"flags\":[],\"custom_flags\":[],\"is_mounted\":false,\"is_to_mount_at_startup\":false,\"type\":\"ADDON\",\"device_id\":\"$PART_ID\"}" \
     -w "\nHTTP:%{http_code}\n"
   ```

   Expect `HTTP:200` and `is_mounted:true` for `PART_ID`.

5. Poll for reconciliation and the Samba soft restart for up to 30 s, then inspect and test the share:
   ```bash
   curl -s http://192.168.0.68:3000/api/shares | jq --arg s "$TEST_SHARE" \
     '.[] | select(.name==$s) | {name, path: .mount_point_data.path, status}'
   ssh root@192.168.0.68 "docker exec app_local_sambanas2 testparm -s 2>&1" \
     | grep -i -A8 "\[$TEST_SHARE\]"
   printf 'transfer-addon-%s\n' "$TS" > /tmp/srat-transfer-back-src.txt
   smbclient "//192.168.0.68/$TEST_SHARE" -U "$TEST_USER%$TEST_PASS" \
     -c "put /tmp/srat-transfer-back-src.txt back-$TS.txt; get back-$TS.txt /tmp/srat-transfer-back-read.txt"
   cmp -s /tmp/srat-transfer-back-src.txt /tmp/srat-transfer-back-read.txt && echo ROUNDTRIP_OK
   ```
   Expected behavior: `path` updated to `ADDON_PATH`, `status.is_valid:true`, share present in `smb.conf`, and `ROUNDTRIP_OK`. Current failure: the stale `HA_PATH` is retained, `status.is_valid:false`, and the client cannot write.

**Assertions:**

- HA unmount and addon mount both succeed for the same device
- Share re-associated with `ADDON_PATH` and `status.is_valid:true`
- Share present in `smb.conf` and writable/readable by `TEST_USER`
- No new ERROR in addon logs

## Validation

1. Record pass or fail with the share API response, `testparm` output, and `smbclient` output as evidence.
2. Clean up in order: delete the test user and share via the API; unmount the addon mount; confirm `ha mounts info` has no `srat_transfer_back`.
3. Confirm `GET /api/volumes` and `GET /api/shares` no longer contain test entries.

> Known log noise: a `supervisor_service.go` `Mounting error ... mount_activation_error` may appear when the share is created. It is environment-specific and does not affect the SMB export.

**Success criteria:** The share remains visible and writable after the ownership change, and cleanup restores the baseline state.
