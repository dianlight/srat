# Test Case: 003.013_ntfs-force-user-persists-after-restart

## Test Objective

Verify the srat#1391 fix persists across an addon restart: an NTFS-backed share still omits `force user`/`force group` in `smb.conf` after the addon (and its fx graph) is restarted, while an ext4-backed share keeps them. Guards against fx-wiring regressions where `MountFlagProber` is nil and every share falls back to `root`.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `state: started`; `curl -s http://192.168.0.68:3000/api/health` → 200 with `alive:true`
2. An NTFS partition is available with mount data (`fstype` `ntfs`/`ntfs3`/`fuseblk`). Reuse the `SRATNTFS01` volume if present, otherwise pick a spare data partition (`system:false`) and export `TEST_PARTITION_ID` (confirm format with user first — do not format without approval).
3. An ext4-backed share exists for the negative control (e.g. `ATA_WD_PC_SN740_SDDPNQD_512G_2006_23482W805056_PART2`). If none exists, note it and use any `usage:internal` ext4 share.
4. Record pre-test smb.conf state: `docker exec app_local_sambanas2 sh -c 'grep -c "^\\[" /etc/samba/smb.conf'`.

**If any preparation step fails** (addon not running, no NTFS volume and user declines format), the test must be **skipped**.

## Execution

1. Ensure the NTFS partition is mounted: `GET /api/volumes` → partition `mount_point_data` entry has `is_mounted:true` and `fstype` `ntfs3` (or alias). If unmounted, mount with the full `mountPointData` object from `GET /api/volumes` (empty `flags`/`custom_flags` to exercise defaults) → 200, `is_mounted:true`.
2. Ensure an NTFS test share exists on the mount path (create via `POST /api/share` with the full `MNT` object from `GET /api/volumes`, `usage:media`, if missing) → 201. Export `TEST_SHARE_NAME`.
3. Verify pre-restart baseline: `docker exec app_local_sambanas2 sh -c 'sed -n "/^\\[<SHARE_UPPER>\\]/,/^$/p" /etc/samba/smb.conf'` → NO `force user` / `force group` lines in the NTFS section; ext4 control section STILL contains `force user = root` / `force group = root`.
4. Restart the addon: `ha addons restart local_sambanas2` (or stop + start). Wait ~30 s, then `curl -s http://192.168.0.68:3000/api/health` → `alive:true`.
5. Re-inspect smb.conf: NTFS share section → still NO `force user`/`force group` lines; DEBUG line for the share shows `"fs":"ntfs3"` (or alias) with no `force_user`/`force_group` keys. Ext4 control → still keeps `force user = root`.

**Assertions:**

- Pre-restart NTFS section omits `force user`/`force group`
- Post-restart NTFS section still omits them (wiring survived restart)
- Ext4 control keeps `force user = root` / `force group = root` before and after
- No `ERROR`/`panic` in addon logs around the restart (excluding known SMART USB-bridge warnings)

## Validation

1. Write smoke (direct FS): `docker exec app_local_sambanas2 sh -c "echo hello > /mnt/<ntfs-path>/.srat_ntfs_restart_test && cat /mnt/<ntfs-path>/.srat_ntfs_restart_test && rm /mnt/<ntfs-path>/.srat_ntfs_restart_test"` → `hello` with no I/O error.
2. Logs: `ha addons logs local_sambanas2` tail → no `ERROR/panic` for mount/share/config related to the restart; `ha core logs` → no `custom_components.srat` tracebacks.
3. Cleanup: delete the test share if created for this run (`DELETE /api/share/${TEST_SHARE_NAME}` → 204); leave the partition in its pre-test mount state. Record deviations in evidence.

**Success criteria:** NTFS force-user omission survives an addon restart; ext4 control unchanged; write smoke passes; logs clean.
