# Test Case: 009.002_factory-reset-with-and-without-protection

## Test Objective

Verify factory reset (wipe addon database back to first-install state) with protection mode OFF and ON: seeded state (custom settings, extra user, extra share) is fully discarded after the wipe, first-install defaults and SetupWizard conditions return, protection gating holds immediately after reset (external mount/format 403 only when ON), and the pre-reset backup restores cleanly afterwards.

> **Note:** the addon exposes a canonical `factory_reset` option (boolean, default `false`):
> setting it to `true` and restarting deletes the SQL database, all configurations,
> settings and update files, then reboots with defaults. Prefer this over manual
> `rm /config/config.db3` — manual removal is only a fallback if the option path fails.

## Preparation

1. Ensure addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Record current protection state: `ha addons info local_sambanas2 | grep -i protected` → note `ORIG_PROTECTED` (restore at the end)
3. Seed known state to prove the reset discards it:
   ```bash
   export API=http://192.168.0.68:3000
   ORIG_SETTINGS=$(curl -s $API/api/settings)
   echo "$ORIG_SETTINGS" | jq -r '.workgroup'  # note ORIG_WORKGROUP
   SEED_WG="RST$(date +%s | tail -c 4)"
   echo "$ORIG_SETTINGS" | jq --arg w "$SEED_WG" '.workgroup=$w' > /tmp/seed-settings.json
   curl -X PUT $API/api/settings -H "Content-Type: application/json" -d @/tmp/seed-settings.json -w "\nHTTP:%{http_code}\n"  # expect 200
   curl -s $API/api/settings | jq -r '.workgroup'  # expect $SEED_WG
   ```
   Optionally seed a user/share (`POST /api/user`, `POST /api/share`) and record their names as `SEED_USER`/`SEED_SHARE`; they must be gone after reset
4. Backup the seeded DB: `ssh root@192.168.0.68 "docker exec app_local_sambanas2 sh -c 'cp /config/config.db3 /config/config.db3.pre-009-002.bak && sha256sum /config/config.db3 /config/config.db3.pre-009-002.bak'"` → both checksums equal; save as `SEED_DB_SUM`. **Also snapshot for reconstruction fallback:** `curl -s $API/api/settings -o /tmp/seed-settings-full.json` and `curl -s $API/api/shares -o /tmp/seed-shares.json` (see `009.001` Validation step 1 for the rebuild procedure if the `.bak` is lost)
5. Verify seed visible: `GET /api/settings` shows `workgroup==$SEED_WG`; `GET /api/users` / `GET /api/shares` contain `SEED_USER`/`SEED_SHARE` if created

**If any preparation step fails** (cannot seed settings, DB backup mismatch, API unreachable), the test must be **skipped** and documented in test logs.

## Execution

For each protection mode in order `OFF` then `ON` (re-seed at the start of the ON loop if the OFF loop already wiped: repeat Preparation step 3 quickly with a new `SEED_WG`):

1. Set protection mode: Supervisor security API `POST /addons/local_sambanas2/security {"protected": false}` (OFF loop) or `{"protected": true}` (ON loop) from inside the addon container, then `ha addons restart local_sambanas2` → wait 12 s → health 200; confirm mode via `ha addons info local_sambanas2 | grep -i protected`
2. Factory reset via the canonical addon option: `ha addons options local_sambanas2 --set factory_reset=true` (verify with `ha addons info local_sambanas2 | grep -i factory`) → `ha addons restart local_sambanas2` → wait 20 s → `curl -s $API/api/health` → 200. Fallback only if the option path fails: `ha addons stop local_sambanas2` → wait 5 s → delete via the **host path** (container is removed on stop, `docker exec` fails): `ssh root@192.168.0.68 'rm -f /addon_configs/local_sambanas2/config.db3 /addon_configs/local_sambanas2/config.db3-shm /addon_configs/local_sambanas2/config.db3-wal'` → `ha addons start local_sambanas2` → wait 12 s.
   > ⚠️ **Never use a glob like `config.db3*`** — it also deletes the `.pre-009-002.bak` backup. List the three filenames explicitly. (Proven 2026-09-17: a `config.db3*` glob destroyed the only backup during `009.001`; the test-box DB had to be reconstructed from API snapshots.)
   > After a successful option-based reset, set `factory_reset=false` again so the next restart does not wipe (`ha addons options local_sambanas2 --set factory_reset=false`)
3. Verify clean reset logs: `ha addons logs local_sambanas2 | tail -n 60 | grep -iE "panic|FATAL"` → empty; startup line present; no `permission denied` for `/data`
4. Verify seed is gone and defaults are back:
   ```bash
   curl -s $API/api/settings | jq -r '.workgroup'  # must NOT equal $SEED_WG
   curl -s $API/api/users | jq -e --arg u "${SEED_USER:-__none__}" 'map(select(.username==$u)) | length == 0'
   curl -s $API/api/shares | jq -e --arg s "${SEED_SHARE:-__none__}" 'map(select(.name==$s)) | length == 0'
   curl -s $API/api/users | jq -e '.[] | select(.is_admin==true) | .has_default_password == true'
   curl -s $API/api/settings | jq -e '.hostname == "" or .hostname == null or .workgroup == "" or .workgroup == null'
   ```
   Record all values as evidence
5. Verify reads work in both modes: `GET /api/volumes` → 200; `GET /api/shares` → JSON array
6. Verify protection gating immediately after reset (same probe as `009.001` step 6):
   - OFF loop: external mount/format attempt must NOT return `Operation not permitted in protected mode`; record status + body
   - ON loop: same attempt must return HTTP 403 with a clear protection/privilege/mount message; record status + body; no `panic`/`FATAL` after the blocked call

**Assertions:**

- Seeded `workgroup`/`SEED_USER`/`SEED_SHARE` are gone after each reset; defaults (`has_default_password:true`, unset `hostname`/`workgroup`) are back (wizard `needsBaseConfig` true)
- Health 200 with no `panic`/`FATAL` in both modes
- Reads (`/api/volumes`, `/api/shares`) 200 in both modes
- External mount/format: not protection-blocked when OFF; 403 + clear message when ON

## Validation

1. Restore seeded DB **while the container is stopped** (host path): `ha addons stop local_sambanas2` → wait 5 s → `ssh root@192.168.0.68 "cp /addon_configs/local_sambanas2/config.db3.pre-009-002.bak /addon_configs/local_sambanas2/config.db3 && rm -f /addon_configs/local_sambanas2/config.db3-shm /addon_configs/local_sambanas2/config.db3-wal && sha256sum /addon_configs/local_sambanas2/config.db3"` → checksum equals `SEED_DB_SUM` → `ha addons start local_sambanas2` → wait 12 s → health 200 → `GET /api/settings | jq -r .workgroup` equals last `SEED_WG`; `SEED_USER`/`SEED_SHARE` present again if created. If the `.bak` is missing, reconstruct from the Preparation snapshots (`PUT /api/settings`, re-`POST` shares with live mount data — see `009.001` Validation step 1) and record the deviation
2. Restore protection state to `ORIG_PROTECTED` (Supervisor security API + restart if changed) → confirm via `ha addons info`; ensure `factory_reset=false` (`ha addons info local_sambanas2 | grep -i factory` → `false`) so a later restart does not wipe again
3. Check logs after restore: addon logs `tail -n 30 | grep -iE "panic|FATAL"` → empty; core logs `tail -n 20` → no new `custom_components.srat` traceback
4. Remove the backup only after successful restore verification; if restore fails, keep `/config/config.db3.pre-009-002.bak` and mark the case `fail` with logs. Optionally clean up seeded user/share via API if the operator prefers pristine state over seeded state (record the choice)

**Success criteria:** Seed discarded and defaults restored after each reset in both modes, protection gating symmetric (OFF allows / ON 403s), seeded DB and original protection state restored, no log errors.
