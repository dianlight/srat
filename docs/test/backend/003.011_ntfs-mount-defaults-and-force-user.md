# Test Case: 003.011_ntfs-mount-defaults-and-force-user

## Test Objective

Verify NTFS mount defaults and Samba force-user behavior for issue #1264 (hassio-addons#769): mounting an NTFS partition applies adapter-declared default mount flags (no root-only lockout), and the generated `smb.conf` omits `force user`/`force group` for NTFS-backed shares so Windows access control entries are honored.

## Preparation

1. Addon running: `ha addons info local_sambanas2` → `state: started`; `curl -s http://192.168.0.68:3000/api/health` → 200 with `alive:true`
2. Target partition (may require format — confirm with user first): pick a spare data partition (`system:false`) and export `TEST_PARTITION_ID`. If no NTFS partition exists, format the agreed spare to NTFS:
   ```bash
   curl -s -X POST http://192.168.0.68:3000/api/filesystem/format -H "Content-Type: application/json" -d "{\"partitionId\":\"$TEST_PARTITION_ID\",\"fstype\":\"ntfs\",\"label\":\"SRATNTFS01\",\"force\":false,\"verbose\":true}"
   ```
   Poll `GET /filesystem/state?partition_id=$TEST_PARTITION_ID` up to 120s → `isClean:true`.
3. Ensure partition is unmounted before mount test (via UI UNMOUNT or `DELETE /api/volume?mount_path=<path>`). If a share is attached (`share != null`), delete it first.

**If any preparation step fails** (no agreed spare partition, user declines format, addon not running), the test must be **skipped**.

## Execution

1. Mount with empty flags (defaults path): `POST /api/volume/mount` with `mountPointData` for `$TEST_PARTITION_ID` and empty `flags`/`custom_flags` → 200, `is_mounted:true`.
2. Verify default flags applied at OS level: `docker exec app_local_sambanas2 sh -c 'cat /proc/mounts | grep $TEST_PARTITION_ID'` → mount options include the NTFS adapter defaults (`fmask=000,dmask=000`), and NOT a bare root-only mapping.
3. Verify API reflects defaults: `GET /api/volumes | jq --arg pid "$TEST_PARTITION_ID" '.[] | select(.partitions[$pid]!=null) | .partitions[$pid].mount_point_data | to_entries[0].value | {fstype, custom_flags}'` → `fstype` is `ntfs`/`ntfs3`/`fuseblk`, flags coherent with mount options.
4. Create a test share on the mount path (via UI or `POST /api/shares`), then regenerate config and inspect: `docker exec app_local_sambanas2 sh -c 'grep -A8 "\[<SHARENAME>\]" /etc/samba/smb.conf'` → NO `force user` / `force group` lines in the NTFS share section.
5. Negative control: an ext4-backed share section STILL contains `force user = root` / `force group = root`.

**Assertions:**

- Mount with empty flags succeeds and OS mount options carry NTFS defaults
- NTFS share section has no `force user`/`force group` lines
- ext4 share section keeps `force user = root` / `force group = root`
- `GET /api/volumes` agrees with `/proc/mounts` on fstype and mount state

## Validation

1. Write smoke (direct FS): `docker exec app_local_sambanas2 sh -c "echo hello > /mnt/$TEST_PARTITION_ID/.srat_ntfs_test && cat /mnt/$TEST_PARTITION_ID/.srat_ntfs_test && rm /mnt/$TEST_PARTITION_ID/.srat_ntfs_test"` → `hello` with no I/O error.
2. Logs: `ha addons logs local_sambanas2` tail → no `ERROR/panic` for mount/share/config; `ha core logs` → no `custom_components.srat` tracebacks.
3. Cleanup: delete the test share; leave the partition mounted (record final state) or restore the pre-test mount state. Record deviations in evidence.

**Success criteria:** NTFS defaults applied on mount; NTFS share omits force-user lines while ext4 keeps them; write smoke passes; logs clean.
