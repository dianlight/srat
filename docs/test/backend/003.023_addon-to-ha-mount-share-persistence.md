# Test Case: 003.023_addon-to-ha-mount-share-persistence

## Test Objective

Verify that a share with a read/write user survives a change of mount ownership from the addon to Home Assistant: after the addon unmounts a volume and HA mounts the same device under an HA-owned path, the share must remain valid, visible, and writable by its configured read/write user.

> Status note: device-based share re-association and persisted path repair are now implemented in `GetSharesByDeviceID`, `ReassociateShareMount`, the `OnMountPoint` handler, and `enrichSharePartitionFromCache`. This case is ready for verification. An earlier run was blocked because the 003.022 setup omitted `fstype`; that test specification is now corrected to pass the filesystem type reported by the volumes API.

## Preparation

These steps assume protection mode is **off**. Confirm it from inside the addon with `curl -s http://supervisor/addons/local_sambanas2/info -H "Authorization: Bearer $SUPERVISOR_TOKEN" | jq '.data.protected'` → `false`. If it is `true`, set it to `false` with `POST http://supervisor/addons/local_sambanas2/security` and body `{"protected":false}`, restart the addon, recreate the port `3000` forward, and confirm `GET /api/problems` does not contain `protected_mode`.

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `started`; health check → `200`.
2. Complete the setup in `003.022_addon-mount-automount-rw-share-external-write` up to its successful external write. Record `PART_ID`, `MNT_PATH`, `TEST_SHARE`, `TEST_USER`, and `TEST_PASS`.
3. Confirm `ha mounts add --help` supports `--type disk` and `--device`.
4. Record the device path: `DEVICE="/dev/disk/by-id/$PART_ID"`; verify it exists: `test -e "$DEVICE"` → exit `0`.
5. Use a fresh HA mount name that has no pre-existing row in `GET /api/volumes`, for example `HA_MOUNT="srat_t23_$(date +%s)"`. Stale rows for a previously used name suppress the mount event needed for re-association. Do not reuse `srat_transfer_test` unless `GET /api/volumes` has no row for that name.

**If any preparation step fails**, the test must be **skipped**.

## Execution

1. Unmount the volume with SRAT (the addon owns this path, so the request is allowed):

   ```bash
   curl -s -X DELETE "http://192.168.0.68:3000/api/volume?mount_path=$MNT_PATH" \
     -w "\nHTTP:%{http_code}\n"
   ```

   Expect `HTTP:200`; `GET /api/volumes` shows `is_mounted:false` for `PART_ID`.

2. Mount the same device through Home Assistant:

   ```bash
   ha mounts add "$HA_MOUNT" --type disk --device "$DEVICE"
   ```

   Expect success; `ha mounts info --raw-json` lists `HA_MOUNT`.

3. Discover the new HA path from `GET /api/volumes`:

   ```bash
   curl -s http://192.168.0.68:3000/api/volumes | jq -c --arg device_id "$PART_ID" '
     [ .[] as $disk | $disk.partitions[]? | .mount_point_data // {} | to_entries[]
       | select(.value.device_id == $device_id) | .value ]
     | map(select(.is_ha_mounted == true)) | first'
   ```

   Save the resulting `path` as `HA_PATH`; it must start with `/media/`, `/share/`, or `/backup/`. Assert `is_mounted:true` and `is_ha_mounted:true`. If the API has not surfaced the new HA mount, use `ha mounts info --raw-json | jq -r --arg mount "$HA_MOUNT" '.[] | select(.name==$mount) | .user_path'` as `HA_PATH` and record this fallback as a deviation.

   Samba exports names in uppercase with hyphens replaced by underscores. Use `EXPORTED_NAME=$(printf '%s' "$TEST_SHARE" | tr '[:lower:]-' '[:upper:]_')` for `smbclient` and the `testparm` section lookup. The `smbclient` binary is available inside the addon container; connect to `//192.168.0.68` from there.

4. Poll for reconciliation and the Samba soft restart for up to 30 s instead of a fixed 12 s wait, then inspect the share:

   ```bash
   curl -s http://192.168.0.68:3000/api/shares | jq --arg s "$TEST_SHARE" \
     '.[] | select(.name==$s) | {name, path: .mount_point_data.path, status}'
   ssh root@192.168.0.68 "docker exec app_local_sambanas2 testparm -s 2>&1" \
     | grep -i -A8 "\[$TEST_SHARE\]"
   ```

   Expected behavior: `status.is_valid:true`, `path` equal to `HA_PATH`, and a `smb.conf` section for the share. Current behavior: `status.is_valid:false`, the stale `MNT_PATH` is retained, and the section is absent.

5. Write from the external client as the configured read/write user:
   ```bash
   printf 'transfer-ha-%s\n' "$TS" > /tmp/srat-transfer-src.txt
   smbclient "//192.168.0.68/$TEST_SHARE" -U "$TEST_USER%$TEST_PASS" \
     -c "put /tmp/srat-transfer-src.txt transfer-$TS.txt; get transfer-$TS.txt /tmp/srat-transfer-back.txt"
   cmp -s /tmp/srat-transfer-src.txt /tmp/srat-transfer-back.txt && echo ROUNDTRIP_OK
   ```
   Expected: `ROUNDTRIP_OK`. Current failure: the share is not exported, so `smbclient` reports `NT_STATUS_BAD_NETWORK_NAME` or `NT_STATUS_LOGON_FAILURE`.

**Assertions:**

- HA mount created and detected with `is_ha_mounted:true`
- Share re-associated with `HA_PATH` and `status.is_valid:true`
- Share present in `smb.conf` and writable/readable by `TEST_USER`
- No new ERROR in addon logs

## Validation

1. Record whether the case passed or failed and capture the share API response, `testparm` output, and `smbclient` output as evidence.
2. Clean up in order: remove the `HA_MOUNT` HA mount with `ha mounts remove`; delete the test user and share via the API; restore the addon mount and automount state from preparation.
3. Confirm `ha mounts info` has no mount named `HA_MOUNT` and `GET /api/volumes` has no active HA-owned row for `PART_ID`.

> Known log noise: a `supervisor_service.go` `Mounting error ... mount_activation_error` may appear when the share is created. It is environment-specific and does not affect the SMB export.

**Success criteria:** The share remains visible and writable after the ownership change, and cleanup leaves no test mount, user, or share behind.
