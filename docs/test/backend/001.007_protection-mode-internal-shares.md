# Test Case: 001.007_protection-mode-internal-shares

## Test Objective

Verify base share functionality with HA addon protection mode ON (issue dianlight/hassio-addons#730): internal HA paths (config, share, media, backup, SSL) remain shareable via the SRAT API with per-user R/RW semantics, while external disk mount/format operations are blocked gracefully (clear 4xx, no panic). Pass/fail split: internal-share success = pass; external-mount blocked with clear error = expected-pass; external-mount succeeding silently or unclear error = fail.

## Preparation

1. Ensure protection mode is ON: `ha addons info local_sambanas2 | grep -i protected` → `true`; if OFF, enable via Supervisor (`ha addons options` / Supervisor UI → Protection mode ON) then `ha addons restart local_sambanas2` → wait 10 s
2. Ensure addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
3. Confirm no external disks are mounted in the container: `ssh root@192.168.0.68 "docker exec app_local_sambanas2 sh -c 'ls /mnt/ 2>&1; df -h | grep -c /mnt || true'"` → record baseline (expect empty or only internal binds)
4. List internal candidate paths: `GET /api/volumes` → note internal entries (config/share/media/backup); pick one with `share==null` as `MNT` object (same jq pattern as `001.001` step 4, but against the internal entry)
5. Set up test environment variables:
   ```bash
   export SRAT_TEST_MODE=true
   export TEST_SHARE_NAME="prot-test-$(date +%s)"
   ```
6. Verify API endpoint is accessible: `curl -s http://192.168.0.68:3000/api/shares | jq '.'` - should return JSON array

**If any preparation step fails** (cannot enable protection mode, API unreachable), the test must be **skipped** and documented in test logs.

## Execution

1. Create an internal share via API (use the `MNT` object from preparation):
   ```bash
   PAYLOAD=$(echo "$MNT" | jq --arg n "$TEST_SHARE_NAME" '{name:$n, mount_point_data:., usage:"media", guest_ok:true, timemachine:false}')
   curl -X POST http://192.168.0.68:3000/api/share \
     -H "Content-Type: application/json" \
     -d "$PAYLOAD" -w "\nHTTP:%{http_code}\n"
   ```
2. Verify API response returns HTTP 201 Created
3. Verify share appears in listing: `curl -s http://192.168.0.68:3000/api/shares | jq -r ".[].name"` includes `${TEST_SHARE_NAME}`
4. Verify `smb.conf` contains the new share (allow ~5-10 s for async soft restart):
   ```bash
   sleep 5; ssh root@192.168.0.68 "docker exec app_local_sambanas2 testparm -s 2>&1 | grep -i -A5 \"${TEST_SHARE_NAME}\""
   ```
5. Attempt an external mount operation (e.g. `POST /api/volumes/mount` or format with an external device id, whichever route exists): expect HTTP 4xx with a clear error message mentioning protection/privilege/mount; record status code + body
6. Verify no `panic`/`FATAL` in addon logs after the blocked mount: `ha addons logs local_sambanas2 | tail -n 50 | grep -iE "panic|FATAL"` → empty

**Assertions:**

- Internal share: API returns 201, `smb.conf` contains share (case-insensitive), share listed via `GET /api/shares`
- External mount/format: rejected with 4xx + clear message (expected-pass); success or cryptic 500 = fail
- No `panic`/`FATAL` in addon logs after blocked operation
- Reporter use case: created internal share is accessible via Samba client (`smbclient -L //192.168.0.68 -U guest%` lists it when `guest_ok:true`)

## Validation

1. Confirm share accessible via Samba client (if guest_ok): `smbclient -L //192.168.0.68 -U guest%`
2. Check addon logs for ERROR correlating with internal share creation: `ha addons logs local_sambanas2 | tail -n 50 | grep -iE "ERROR"` → no new errors for the 201 path (mount-blocked 4xx log lines are expected and not failures)
3. Clean up: remove test share via API `DELETE http://192.168.0.68:3000/api/share/${TEST_SHARE_NAME}` → 204; verify `GET /api/shares` no longer contains it and `testparm -s` section removed after ~5 s
4. Leave protection mode ON (restore to OFF only in suite teardown step)

**Success criteria:** Internal share created, listed, in `smb.conf`, accessible, then cleaned up; external mount blocked gracefully with no panic; per the agreed split, blocked-external counts as expected-pass.
