# Test Case: 003.018_ha-mount-reflected-without-restart

## Test Objective

Verify that HA-managed mount state changes (add, remove, modify) are reflected in `GET /api/volumes` without requiring the SRAT addon to be restarted. The test ensures that the volume service observes the actual mount state via `/proc/self/mountinfo` or equivalent and updates SRAT's internal state accordingly.

## Preparation

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `started`; health 200
2. Confirm at least one HA-managed partition exists (HA mount path under `/media/`, `/share/`, or `/backup/`) with `is_ha_mounted: true` in `GET /api/volumes`
3. Record the HA mount path (e.g., `HA_PATH=/media/ha_usbtest`) and its corresponding SRAT partition ID
4. Confirm the SRAT addon is **not** restarted during the test (no `ha_restart_addon`)

**If any preparation step fails**, the test must be **skipped**.

## Execution

1. `GET /api/volumes` → 200; record initial state of the HA-managed partition (`mount_point`, `is_ha_mounted`, status)
2. Trigger an HA mount change **without restarting** the addon:
   - Option A: Add a new HA mount via `ha mounts add --type cifs --device /dev/sdx1 --path /media/ha_usbtest2` (if path doesn't exist)
   - Option B: Remove an existing HA mount via `ha mounts remove /media/ha_usbtest` (if exists)
   - Option C: Modify an existing HA mount via `ha mounts update` (if supported)
3. Wait for the change to propagate (typically < 5s for udev events, or up to 10s for polling if no udev event)
4. `GET /api/volumes` → 200; verify the affected partition's state has been updated:
   - If added: new partition should appear with correct `is_ha_mounted: true` and `mount_point` matching the HA path
   - If removed: partition should show `is_ha_mounted: false` or be absent from the list
   - If modified: partition's `mount_point` or other state should reflect the change
5. Verify the change is reflected in the frontend Volumes UI (badge, actions availability, etc.)
6. Check addon logs for `SyncPartitionMountData` or `IsHAManagedMountPath` events (no ERROR)

**Assertions:**

- HA mount changes are detected and reflected in `GET /api/volumes` within 10 seconds
- `is_ha_mounted` flag matches the actual mount state (true when HA-managed, false otherwise)
- `mount_point` values are accurate (HA paths under `/media/`, `/share/`, `/backup/`; SRAT paths under `/mnt/`)
- No restart of the SRAT addon is required for the state to update
- No ERROR in addon logs during the test

## Validation

1. Confirm addon state `started` and health 200 before and after the test
2. Verify no mutations (POST/PUT/DELETE) were issued during the test (state should be read-only)
3. Check browser console for errors and take a screenshot showing the updated volume state

**Success criteria:** HA mount state changes are reflected in the SRAT volumes API without requiring the addon to be restarted; all assertions pass; logs are clean.

# Test Case: 003.019_restart-reconciliation-of-ha-mount-rows

## Test Objective

Verify that SRAT reconciles HA-managed mount rows during addon restart, ensuring that duplicate or stale rows are properly cleaned up and that the correct mount path is reflected in the volumes API. This test validates the reconciliation logic that runs on addon restart and the mount-table watcher that detects changes in `/proc/self/mountinfo`.

## Preparation

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `started`; health 200
2. Confirm at least one HA-managed partition exists with `is_ha_mounted: true` in `GET /api/volumes`
3. Record the initial state of the HA mount (path, partition ID, `is_ha_mounted`, `is_mounted`)
4. Confirm the SRAT addon is **not** in a protected/restricted state (protection mode OFF)
5. Note the current `ha mounts info --raw-json` output for reference

**If any preparation step fails**, the test must be **skipped**.

## Execution

1. `GET /api/volumes` → 200; record initial state of the HA-managed partition (`mount_point`, `is_ha_mounted`, status)
2. Restart the SRAT addon:
   - `ha_restart_addon` (via MCP tool or `ha addons restart local_sambanas2`)
   - Wait for addon to reach `started` state again (typically 5-10s)
3. `GET /api/volumes` → 200; verify:
   - HA-managed partition is still present (if it was HA-mounted before restart)
   - `is_ha_mounted` flag is `true` for HA paths
   - `is_mounted` flag reflects the actual mount state (not stale)
   - No orphaned rows (e.g., no duplicate rows for the same device)
   - No phantom rows with `ha=true` and **no backing share**. Share-backed HA rows are legitimate config and must be preserved: the reproduced `/media/srat_test_disk` row is referenced by the `srattestha` and `SRAT_TEST_DISK` shares, so it is not an orphan and must not be pruned by mount reconciliation (#003.019).
4. Verify the volumes UI reflects the correct state (badge, actions availability, etc.)
5. Check addon logs for reconciliation events (e.g., `refresh()`, `unmount`, `disable`, `reconcile`)

**Assertions:**

- HA mount rows are correctly reconciled after restart (no duplicate unshared rows). Share-backed rows are cleaned up through the share-validation path, not by pruning mount rows — deleting a share-backed mount row would orphan its shares.
- `is_ha_mounted` and `is_mounted` flags match the actual mount state
- `mount_point` values are accurate (HA paths under `/media/`, `/share/`, `/backup/`; SRAT paths under `/mnt/`)
- No ERROR in addon logs during the test
- All mount-related actions (unmount, disable, format, check) are available for the HA-managed row (if applicable)

**Success criteria:** SRAT correctly reconciles HA mount rows after restart; no stale or phantom rows remain; all mount state is accurate and reflected in API and UI; logs are clean.

# Test Case: 003.020_create-share-on-ha-mount-prefills-colliding-name-409-inline

## Test Objective

Verify that when creating a share on an HA-managed partition that already has a share with the same name, the Create Share 409 conflict is surfaced inline in the UI (not silently ignored), and that the error message is actionable. This validates the duplicate-name Create Share 409 handling via `addMessage` in the Shares page.

## Preparation

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `started`; health 200
2. Confirm at least one HA-managed partition exists (HA mount path under `/media/`, `/share/`, or `/backup/`) with `is_ha_mounted: true` in `GET /api/volumes`
3. Confirm the partition has **no existing share** with the name that will be used for the test (e.g., `USBTEST`)
4. Create a share on the HA-managed partition with name `USBTEST` via the Volumes UI or API:
   - `POST /api/share` with `{"name": "USBTEST", "mount_point_data": {"path": "/media/ha_usbtest"}}`
   - Confirm success (200) and that the share appears in `GET /api/shares` with status `is_ha_mounted: true`
5. Attempt to create another share with the **same name** `USBTEST` (duplicate name):
   - `POST /api/share` with `{"name": "USBTEST", "mount_point_data": {"path": "/media/ha_usbtest2"}}` (different path, same name)
   - Confirm the request fails with 409 Conflict
6. Verify that the 409 error is displayed inline (e.g., in a toast, error banner, or field-level message) and that the user can see the conflict reason

**If any preparation step fails**, the test must be **skipped**.

## Execution

1. `GET /api/shares` → 200; confirm no existing share named `USBTEST` (or note its ID)
2. `POST /api/share` with `{"name": "USBTEST", "mount_point_data": {"path": "/media/ha_usbtest"}}` → 200; confirm share created
3. `POST /api/share` with `{"name": "USBTEST", "mount_point_data": {"path": "/media/ha_usbtest2"}}` → 409 Conflict
4. Verify:
   - HTTP 409 response code
   - Inline error message appears (e.g., "Share name already exists" or similar)
   - The error message is actionable and visible to the user (not just logged)
   - No silent failure (no UI freeze, no missing error indication)

**Assertions:**

- Duplicate name creates a 409 Conflict response
- Inline error message is displayed (e.g., via `addMessage` in Shares.tsx, toast, or field-level error)
- Error message clearly indicates the conflict (e.g., "Share name already exists")
- User can proceed to resolve the conflict (e.g., by editing or deleting the existing share)

**Success criteria:** Duplicate name triggers 409 with visible inline error; no silent failure; user can see and act on the conflict.
