# Test Case: 009.001_first-install-with-and-without-protection

## Test Objective

Verify clean first-install boot of the SRAT addon with protection mode OFF and ON: fresh database starts without `panic`/`FATAL`, exposes default settings (`hostname`/`workgroup` unset, admin `has_default_password:true`, `telemetry_mode:Ask`), triggers the SetupWizard conditions (`useSetupWizard` → `needsBaseConfig || needsTelemetry`), and enforces protection gating from the first boot (internal API reads work in both modes; external mount/format blocked with 403 only when ON).

## Preparation

1. Ensure addon running: `ha addons info local_sambanas2` → `started`; `curl -s http://192.168.0.68:3000/api/health` → 200
2. Record current protection state: `ha addons info local_sambanas2 | grep -i protected` → note `ORIG_PROTECTED` (restore at the end)
3. Record current DB state for backup: `ssh root@192.168.0.68 "docker exec app_local_sambanas2 sh -c 'ls -la /config/config.db3 && sha256sum /config/config.db3'"` → save `ORIG_DB_SUM`; backup to safe location: `ssh root@192.168.0.68 "docker exec app_local_sambanas2 cp /config/config.db3 /config/config.db3.pre-009-001.bak"` → verify copy exists
4. Verify API baseline before wipe: `curl -s http://192.168.0.68:3000/api/settings | jq -e 'has("hostname") and has("workgroup")'` → true; `curl -s http://192.168.0.68:3000/api/users | jq -r '.[] | select(.is_admin==true) | .username'` → note `ORIG_ADMIN`; **snapshot for reconstruction fallback:** `curl -s $API/api/settings -o /tmp/orig-settings.json` and `curl -s $API/api/shares -o /tmp/shares.json` (if the `.bak` is ever lost, these snapshots + live volume data rebuild the DB — see Validation step 1)
5. Define helpers:
   ```bash
   export API=http://192.168.0.68:3000
   export SSH="ssh root@192.168.0.68"
   ```
6. Ensure no pending wizard-blocking state is required: this test wipes the DB, so confirm with the operator that unsaved addon state may be lost (backup in step 3 covers restore)

**If any preparation step fails** (addon not running, DB not found at `/config/config.db3`, API unreachable), the test must be **skipped** and documented in test logs.

## Execution

For each protection mode in order `OFF` then `ON` (set `PROT=true|false` per loop):

1. Set protection mode: from inside the addon container call Supervisor security API `POST /addons/local_sambanas2/security {"protected": false}` (OFF loop) or `{"protected": true}` (ON loop), then `ha addons restart local_sambanas2` → wait 12 s → `curl -s $API/api/health` → 200; confirm `ha addons info local_sambanas2 | grep -i protected` matches the loop mode
2. Fresh-install simulation: `ha addons stop local_sambanas2` → wait 5 s → delete the database **while the container is stopped** via the host path (the container is removed on stop, so `docker exec` fails): `ssh root@192.168.0.68 'rm -f /addon_configs/local_sambanas2/config.db3 /addon_configs/local_sambanas2/config.db3-shm /addon_configs/local_sambanas2/config.db3-wal'` → `ha addons start local_sambanas2` → wait 12 s → `curl -s $API/api/health` → 200.
   > ⚠️ **Never use a glob like `config.db3*`** — it also deletes the `.pre-009-001.bak` backup. List the three filenames explicitly. (Proven 2026-09-17: a `config.db3*` glob destroyed the only backup; the test-box DB had to be reconstructed from API snapshots.)
3. Verify clean boot logs: `ha addons logs local_sambanas2 | tail -n 60 | grep -iE "panic|FATAL"` → empty; `srat-server started` (or equivalent startup line) present; no `permission denied` for `/data`
4. Verify first-install defaults via API (wizard trigger conditions):
   ```bash
   curl -s $API/api/settings | jq -e '.hostname == "" or .hostname == null or .workgroup == "" or .workgroup == null'
   curl -s $API/api/users | jq -e '.[] | select(.is_admin==true) | .has_default_password == true'
   curl -s $API/api/settings | jq -r '.telemetry_mode'  # expect Ask (wizard shows telemetry step when internet reachable)
   ```
   At least `has_default_password:true` plus unset `hostname`/`workgroup` must hold (`needsBaseConfig`); record values as evidence
5. Verify reads work in both modes: `curl -s $API/api/volumes -w "\nHTTP:%{http_code}\n"` → 200; `curl -s $API/api/shares | jq type` → `array`
6. Verify protection gating from first boot:
   - OFF loop: external mount attempt (e.g. `POST /api/volumes/mount` with a real unmounted partition, or format dry-run if available) must NOT be rejected with `Operation not permitted in protected mode`; record status + body
   - ON loop: same external mount/format attempt must be rejected with HTTP 403 and a clear message mentioning protection/privilege/mount; record status + body; `ha addons logs local_sambanas2 | tail -n 30 | grep -iE "panic|FATAL"` → empty after the blocked call
7. Complete the wizard minimally via API so the next loop starts from a known state (or wipe again at loop start — wiping at step 2 already covers it; this step only applies if re-wipe is skipped): `PUT /api/settings` with valid `hostname`/`workgroup`, `PUT /useradmin` to set a known admin password, then confirm `has_default_password:false`

**Assertions:**

- Fresh DB boots to 200 health with no `panic`/`FATAL` in both protection modes
- First-install defaults hold: admin `has_default_password:true`, `hostname`/`workgroup` unset (wizard `needsBaseConfig` true)
- `GET /api/volumes` and `GET /api/shares` return 200 in both modes (reads never blocked)
- External mount/format: allowed-or-unrelated-error when OFF; 403 + clear protection message when ON (no panic)

## Validation

1. Restore original DB **while the container is stopped** (host path): `ha addons stop local_sambanas2` → wait 5 s → `ssh root@192.168.0.68 "cp /addon_configs/local_sambanas2/config.db3.pre-009-001.bak /addon_configs/local_sambanas2/config.db3 && rm -f /addon_configs/local_sambanas2/config.db3-shm /addon_configs/local_sambanas2/config.db3-wal && sha256sum /addon_configs/local_sambanas2/config.db3"` → checksum equals `ORIG_DB_SUM` → `ha addons start local_sambanas2` → wait 12 s → health 200 → `GET /api/users` shows `ORIG_ADMIN` again. If the `.bak` is missing (glob accident), reconstruct instead: `PUT /api/settings` with a saved settings snapshot, re-`POST` custom shares from a saved `GET /api/shares` snapshot using **live** `mount_point_data` from `GET /api/volumes` (mount partitions first — exfat needs `modprobe exfat` in the container; share-create 422s against stale/unmounted mount data), then set the admin password to a known value and record it
2. Restore protection state to `ORIG_PROTECTED` (Supervisor security API + restart if changed) → confirm via `ha addons info local_sambanas2 | grep -i protected`
3. Check logs after restore: `ha addons logs local_sambanas2 | tail -n 30 | grep -iE "panic|FATAL"` → empty; `ha core logs | tail -n 20` → no new `custom_components.srat` traceback
4. Remove the backup only after successful restore verification (`rm /config/config.db3.pre-009-001.bak`); if restore fails, keep the backup and mark the case `fail` with logs

**Success criteria:** Clean first boot in both modes with wizard defaults present, reads working in both modes, external ops blocked with 403 only when ON, original DB and protection state restored, no log errors.
