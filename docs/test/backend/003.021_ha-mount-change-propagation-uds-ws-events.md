# Test Case: 003.021_ha-mount-change-propagation-uds-ws-events

## Test Objective

Verify that mount-table changes (including Home Assistant–managed mounts) propagate through the udev event path and WebSocket event bus to API consumers without relying on interval polling. This complements `003.018` (mount reflected without restart) by pinning the _detection_ mechanism: block-level changes arrive as udev events; mount-state reconciliation flows through `PartitionEvent`/`MountPointEvent` → WS broadcast.

## Preparation

1. Ensure the SRAT addon is running: `ha apps info local_sambanas2` → `started`; health 200
2. Confirm the event bus is wired: `GET /api/events` (or equivalent) is reachable and `volumes`/`shares` channels exist
3. Pick an HA-managed partition (if any) or a SRAT-managed unmounted partition (`GET /api/volumes`)

**If any preparation step fails**, the test must be **skipped**.

## Execution

### Part A: Udev-driven mount change

1. `GET /api/volumes` → 200; note current mount state of the target partition
2. Trigger a block-level mount change via SRAT (e.g., `POST /api/volume/mount` on an SRAT-managed partition), or via `ha mounts add` on a disposable partition
3. Wait ≤10 s for the udev ADD event to reach `UdevHandler.HandlePartitionEvent` → `SyncPartitionMountData`
4. `GET /api/volumes` → verify the partition reflects the new mount state within the expected window (no polling fallback involved)
5. Check that the corresponding `PartitionEvent` (Type=ADD/UPDATE) is emitted on the event bus and forwarded over WS to the frontend (`volumes` channel)

**Assertions:**

- udev event → mount sync completes with no error
- Mount state updated in `GET /api/volumes` within 10 s of the change
- A typed `PartitionEvent` with the expected `Type` is emitted
- WS broadcast of the event reaches subscribed clients within 10 s

### Part B: HA-managed mount change (no udev block event expected)

1. Verify that an HA Supervisor–initiated mount does **not** produce a udev block ADD event for the SRAT addon (documented behavior)
2. Confirm the mount still shows correctly via path-prefix ownership (`IsHAManagedMountPath`) and, if present, via the mount table
3. Confirm the reconciliation on the next refresh cycle marks the row appropriately (mounted / HA-managed) and emits `MountPointEvent` (Type=UPDATE) so the frontend live-updates

**Assertions:**

- HA-managed mount detection does not depend on a missed udev event for correctness of the flag
- Mount state transitions emit `MountPointEvent` through the bus (no polling fallback)
- No ERROR in addon logs during the change window

## Validation

1. Addon logs: `ha addons logs local_sambanas2` → no ERROR/stack trace from the event handling path
2. Frontend: Volumes tab live-updates within 10 s after a mount change (WS `volumes` event) without manual reload

**Success criteria:** Mount changes propagate via udev events and WS events within the expected latency; the implementation does **not** rely on interval polling of the mount table.
